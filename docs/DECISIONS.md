# Decisions

Format: Status / Context / Decision / Consequences. Newest first once this grows; append, don't rewrite history — if a decision is reversed, add a new entry that supersedes it rather than editing the old one.

## D-001 — Modular monolith over microservices
**Status:** Accepted
**Context:** The domains (concept graph, question engine, attempts, mastery, autopsy) are read together on nearly every student-facing screen; team size is one for the foreseeable future.
**Decision:** One deployable app, internal module boundaries enforced in code (see [ARCHITECTURE.md](ARCHITECTURE.md) §2, §6).
**Consequences:** Faster iteration now; if a module later needs independent scaling, extraction is possible because boundaries already exist — but that's deferred work, not designed for prematurely.

## D-002 — TypeScript + Next.js + Postgres + Prisma + Redis/BullMQ
**Status:** Accepted
**Context:** Solo/small-team build, AI-heavy background workloads, need for strong typing across UI/API/domain/AI-schema boundaries.
**Decision:** See [ARCHITECTURE.md](ARCHITECTURE.md) §3 for the full table and rationale.
**Consequences:** Locks into a Node/TS ecosystem; acceptable since the domain logic itself is framework-agnostic TS and portable if any single piece needs replacing.

## D-003 — All AI outputs schema-validated via Zod through one provider abstraction
**Status:** Accepted
**Context:** Product rules explicitly forbid fake AI and fake analytics; question generation deals in mathematical correctness, which LLMs are not reliable at unaided.
**Decision:** No call site touches a provider SDK directly; every structured AI output is Zod-validated; question generation includes an independently-recomputed ground truth check, not just LLM self-report. See [AI_ARCHITECTURE.md](AI_ARCHITECTURE.md).
**Consequences:** More upfront plumbing per task type; in exchange, "published" questions have a much stronger correctness guarantee, and provider swaps are cheap.

## D-004 — Auth provider: open, not yet decided
**Status:** Open
**Context:** The likely real-world sign-up path for Indian students skews toward phone/OTP rather than email/password; a managed provider (e.g. Clerk) is faster to ship but may not have great phone-OTP support for Indian numbers out of the box, while a self-hosted solution (Auth.js/NextAuth with a custom OTP provider) is more flexible but more work.
**Decision:** Deferred. Phase 1–3 development proceeds with a single seeded internal test user and no real auth flow, per [MASTER_PLAN.md](MASTER_PLAN.md) Phase 1. This must be decided before Phase 4 (first real student use).
**Consequences:** None yet — explicitly not blocking early work. Revisit before Phase 4.

## D-005 — No confidence score, ever
**Status:** Accepted (product-level constraint, not just technical)
**Context:** Explicit instruction from product vision: the system must not claim to know how a student feels.
**Decision:** No schema field, API response, or UI element represents "confidence." All measurement is of observable performance (accuracy, speed, retries, hint use) — see [DATABASE.md](DATABASE.md) §MasteryState.
**Consequences:** Some product ideas that would naturally want a "how sure are you?" input (e.g. self-reported difficulty) are out unless reframed as an observable proxy instead.

## D-006 — Autopsy output is a hypothesis, structurally, not just in prompt wording
**Status:** Accepted
**Context:** The product must never pretend to know why a student made a mistake.
**Decision:** The `Autopsy` schema has no field that represents a confirmed root cause until `confirmed = true`; anything downstream (mastery updates, repair question selection) that would use root cause is gated on that flag. See [DATABASE.md](DATABASE.md) §Question Autopsy and [AI_ARCHITECTURE.md](AI_ARCHITECTURE.md) §4.
**Consequences:** Repair can only act after student confirmation, which adds a step to the loop but keeps the diagnosis honest.

## D-007 — Question Universe claims taxonomy coverage, not mathematical completeness
**Status:** Accepted
**Context:** "Map the full space of possible questions" is not a well-defined or achievable claim; "cover a curated, explainable taxonomy" is.
**Decision:** `PatternTaxonomyCell` is the unit of coverage tracking; all coverage statistics are computed against this table. See [QUESTION_ENGINE.md](QUESTION_ENGINE.md) §3.
**Consequences:** Coverage numbers are honest but bounded by the quality of the Examiner Lens analysis that produced the taxonomy — garbage-in/garbage-out risk is real and is the reason Lens output gets a human review step in Phase 2.

## D-008 — Human review gate on Examiner Lens and on extreme/novel difficulty tiers, relaxable later
**Status:** Accepted, revisit after Phase 7
**Context:** Bootstrap trust in AI-generated curriculum content and hard/extreme questions is low; a human-in-the-loop gate is cheap insurance early.
**Decision:** Lens analyses require human review before use; Standard/Advanced tier generation can auto-publish after passing the validation pipeline, Hard/Extreme/Novel require human review at launch. See [QUESTION_ENGINE.md](QUESTION_ENGINE.md) §4.
**Consequences:** Slower initial content velocity; the gate is meant to be loosened once rejection-rate data shows the pipeline is reliable (tracked as an explicit go/no-go input in [MASTER_PLAN.md](MASTER_PLAN.md)).

## D-009 — Calendar-aware prep-phase domain model and core calculation move to Phase 1
**Status:** Accepted (supersedes the original Phase 6 placement)
**Context:** The original plan deferred `Student`/`Enrollment`/`PrepPhaseTemplate`/`CatchUpPlan` to Phase 6 alongside the phase UI. On reconciliation against the product vision, this was wrong: distinguishing a September joiner's experience from a December joiner's is foundational to the product's value proposition, not a late enhancement — and `CatchUpPlan` can't be designed correctly without the schema existing from the start.
**Decision:** `Student`, `Enrollment`, `PrepPhaseTemplate`, `CatchUpPlan`, and the `/packages/domain/prep-phase` pure functions (`computePrepPhase`, `applyCatchUp`) are built and unit-tested in Phase 1. Only the phase *UI* stays in Phase 6. See [MASTER_PLAN.md](MASTER_PLAN.md) Phase 1 and Phase 6.
**Consequences:** Phase 1 is slightly larger than originally scoped; in exchange, Phase 6 becomes UI-only and the risk of discovering a calendar-model flaw late (after real enrollment data exists) is largely eliminated.

## D-010 — Attempt timing is event-sourced (`AttemptEvent`), not a set of duration columns
**Status:** Accepted
**Context:** The product needs time as a first-class signal (hint timing, retry timing, time-between-actions, time-before-first-interaction) without knowing in advance every timing question the autopsy/mastery systems will eventually ask.
**Decision:** `AttemptEvent` is a single, generic, append-only event log (`event_type` + `payload: jsonb` + `occurred_at`) and is the source of truth for all interaction/timing history. `Attempt`'s own timestamp and count fields are denormalizations derived from it, kept only where they make common queries cheap. See [DATABASE.md](DATABASE.md) §Attempt & AttemptEvent.
**Consequences:** A new timing signal is a new `event_type`, never a new column or a new table — this is what makes the model "extensible without over-engineering" rather than either under-specified or prematurely elaborate.

## D-011 — `reasoning_text` is a distinct field from `working_steps`, shaped (not built) for future voice input
**Status:** Accepted
**Context:** "What computation did you do" (`working_steps`) and "why did you pick this answer" (`reasoning_text`) are different diagnostic signals for autopsy; conflating them would lose information the hypothesis step needs.
**Decision:** `Attempt.reasoning_text` (free text) is separate from `Attempt.working_steps` (structured scratch/computation). `reasoning_input_mode` (`text` | `voice`) and `reasoning_audio_ref` exist on the schema now so voice input doesn't require a migration later, but voice capture itself is not implemented — `reasoning_input_mode` defaults to `text` and `reasoning_audio_ref` stays null until that phase starts (not before [MASTER_PLAN.md](MASTER_PLAN.md)'s explicit "not building yet" list is revisited).
**Consequences:** Two nullable text-ish fields exist on `Attempt` from Phase 1 with no reader until Phase 5 — an acceptable, explicitly-justified exception to "no speculative fields," since the alternative is a breaking schema change exactly when autopsy work is underway.

## D-012 — `ErrorTaxonomy` is a real table, referenced by foreign key
**Status:** Accepted
**Context:** [AI_ARCHITECTURE.md](AI_ARCHITECTURE.md) already required error classification to be "a controlled taxonomy, not free text," but the original schema stored `Autopsy.error_type` as a bare string, which doesn't actually enforce that.
**Decision:** `ErrorTaxonomy(id, code, label, description)` is a proper table; `Autopsy.error_taxonomy_id` and `RepairPlan.target_error_taxonomy_id` are foreign keys into it, seeded with an initial small set of error codes relevant to Percentages and grown deliberately over time. See [DATABASE.md](DATABASE.md) §Error Taxonomy.
**Consequences:** Adding a new error category is a seed-data change, not a code change or a string-matching risk across the codebase — consistent with how exam structure and content provenance are already handled.

## D-013 — Concept relationships expand to 8 types with rich metadata; error vocabulary is shared between Examiner Lens and Autopsy
**Status:** Accepted
**Context:** Phase 1's `ConceptRelation` had 3 types (`prerequisite_of`, `related_to`, `combines_with`) and a bare `strength` enum — not enough to distinguish, say, "Ratio is required before Percentages" from "Percentages sometimes needs Ratio again for advanced problems" from "Percentages and Probability look similar but shouldn't be combined." Separately, Examiner Lens needed a "what can go wrong" taxonomy (misconception/trap/calculation/interpretation/method-selection), and `ErrorTaxonomy` already existed for Autopsy — building a second, disconnected error vocabulary for Lens would fork a concept that should be singular.
**Decision:** `ConceptRelation.type` expands to 8 values (`prerequisite`, `foundational`, `directly_related`, `commonly_combined`, `application`, `dependent`, `advanced_extension`, `related_but_distinct`), each with `rationale`, `sharedKnowledge`, `usefulForQuestionGeneration`, `requirementLevel`, and `certainty` replacing the single `strength` field. `ErrorTaxonomy` gains a `category` field using the same 5-value vocabulary Examiner Lens error modes use, so both systems key off one table. See [QUESTION_ENGINE.md](QUESTION_ENGINE.md) §1-2 and [DATABASE.md](DATABASE.md).
**Consequences:** `strength` is removed (not deprecated-and-kept) since no live database has ever held data in this column (confirmed empty in every environment through Phase 2 — see the Phase 2 report). Every future error-mode addition, whether authored for teaching content, Examiner Lens traps, or Autopsy diagnosis, goes through one table.

## D-014 — Pattern family (structure) and taxonomy cell (concrete slice) are two levels, not one
**Status:** Accepted
**Context:** Phase 1's `PatternTaxonomyCell` conflated "the kind of question this is" (e.g. "Reverse Percentage") with "this specific combination/trap/difficulty instance" in one flat row (`patternName: string`). The product vision explicitly describes a pattern as something that "can generate many valid questions" — a single flat row can't represent a structure with multiple potential combinations/traps/testing modes.
**Decision:** `QuestionPatternFamily` is a new, first-class table (name, skill, description, expected difficulty, and three "potential" arrays); `PatternTaxonomyCell.patternName` (string) becomes `patternFamilyId` (FK). A family is authored once; cells are the concrete, narrow coverage-tracked instantiations of it. See [QUESTION_ENGINE.md](QUESTION_ENGINE.md) §3.
**Consequences:** One extra join to get from a `Question` to its pattern family's name/skill/description, in exchange for the taxonomy actually being able to express "this family has 2 traps and 3 combinations, and only some slices of that space are covered."

## D-015 — Examiner Lens combinations are always derived from the graph, never stored
**Status:** Accepted
**Context:** An earlier draft of this phase considered a `validCombinations: concept_id[]` column on `ExaminerLensAnalysis` (Phase 1 already had one). Storing it risks the classic cached-derived-data problem: `ConceptRelation` edges can be added, corrected, or reclassified after a Lens analysis is saved, and a stored list would silently go stale.
**Decision:** `ExaminerLensAnalysis` has no combinations column at all. `deriveCombinations(graph, conceptName)` in `@ipmat/examiner-lens` computes it live from `ConceptRelation`, every time it's needed, filtering to types that are actually useful for question generation (`commonly_combined`, `application`, `dependent`) and excluding `related_but_distinct`.
**Consequences:** Same discipline already applied to `MasteryState` (derived, never input) and now to pattern-family coverage (D-016) — a consistent architectural pattern: things that can be computed from a source of truth are computed, not cached as a second source of truth that can drift.

## D-016 — Question DNA finalized: `testingModes`/`noveltyLevel`/`examRelevance` are normalized columns; `trapErrorTaxonomyId` replaces the free-text `trapType`
**Status:** Accepted
**Context:** Phase 1's `Question.transformation` and `trapType` were nullable free-text strings — placeholders acknowledged at the time as needing real structure once Examiner Lens's controlled vocabularies existed. Phase 2 built those vocabularies (`TestingMode`, `ErrorTaxonomy.category`); leaving `Question` on the old placeholder fields would mean Question DNA didn't actually reflect the taxonomy it's supposed to be tagged against.
**Decision:** `Question.transformation` → `testingModes: TestingMode[]` (a question can exercise more than one mode); `Question.trapType` → `trapErrorTaxonomyId` (FK into `ErrorTaxonomy`, same table Autopsy uses); new normalized columns `noveltyLevel` and `examRelevance` (previously not tracked at all) since both are filtered on frequently (novelty-handling practice selection, "is this actually exam-typical" filtering) and belong as indexed columns, not inside the `difficultyDimensions` JSON blob. New `combinesWithConceptIds` array records which concepts a specific question actually combines, distinct from a pattern family's broader "potential" list.
**Consequences:** This is the second schema change to `Question` after Phase 1 (the first being none — Phase 1 shipped it once). Justified because Phase 1's `MASTER_PLAN.md` explicitly named "finalize Question DNA" as Phase 2's job, not a promise that Phase 1's placeholder fields were final.

## D-017 — `@ipmat/ai` has zero dependency on any domain package; its schemas restate rather than import domain shapes
**Status:** Accepted
**Context:** `@ipmat/ai`'s Zod schemas (Examiner Lens output, question candidates) need to match the shapes of `@ipmat/examiner-lens`/`@ipmat/question-engine` types closely. Importing those types directly would create a circular dependency, because the generation pipeline lives in `@ipmat/question-engine` and needs `@ipmat/ai`'s `AiProvider`/`generateStructured` — i.e. `question-engine → ai` must be the only direction.
**Decision:** `@ipmat/ai` restates the small, stable controlled vocabularies (`TestingMode`, `ErrorCategory`, `DifficultyTier`, `DifficultyDimensions`) as its own Zod schemas rather than importing the domain packages' TS types. This is also, independently, the right call at a trust boundary: what an LLM is allowed to produce is a fixed contract that shouldn't silently change just because a domain type gets refactored for an unrelated reason.
**Consequences:** A small amount of duplication (the same ~10-20 string literals exist in two places) that must be kept in sync by hand; a mismatch surfaces immediately as a schema-validation failure on every AI call, not silently, which is an acceptable failure mode for a rare, deliberate vocabulary change.

## D-018 — Untrusted (AI-generated) arithmetic strings are allowlist-filtered before reaching `mathjs.evaluate()`
**Status:** Accepted
**Context:** Independent answer verification (docs/QUESTION_ENGINE.md §5b) needs to recompute a candidate's stated arithmetic without trusting the LLM's claimed answer. `mathjs` had two property-injection advisories (GHSA-29qv-4j9f-fjw5, GHSA-jvff-x2qm-6286, fixed in 15.2.0) — and even patched, evaluating LLM-authored expression strings is evaluating untrusted input by definition.
**Decision:** Pinned `mathjs` to `^15.2.0` (the patched version) AND added a strict regex allowlist (digits, whitespace, `+ - * / ^ ( ) . ,` only) that a computation string must pass before it is evaluated at all — anything else is rejected outright as `impossible_computation`, never passed to `evaluate()`. See `@ipmat/validation/src/verifyComputation.ts`.
**Consequences:** A small class of legitimate-but-unusual arithmetic notation (e.g. scientific notation `1e5`) would currently be rejected rather than evaluated; acceptable for Phase 3's plain percentage arithmetic, revisit if a future pattern family genuinely needs it.

## D-019 — Duplicate-risk detection uses token-overlap (Jaccard) similarity as an interim measure, not embeddings
**Status:** Accepted, revisit when a real content bank exists
**Context:** docs/QUESTION_ENGINE.md's validation pipeline has always named "duplicate/near-duplicate check — embedding similarity" as the real target, but that needs an embedding model and a vector index over a real question bank, neither of which exists yet with only 1-2 questions total.
**Decision:** `checkDuplicateRisk()` in `@ipmat/validation` uses simple token-overlap (Jaccard) similarity against existing question bodies as an honest, deterministic, zero-dependency stand-in.
**Consequences:** Catches near-verbatim reuse (same words, different numbers) but will NOT catch a semantically identical question phrased in entirely different words. This gap is documented in code and here, not hidden — replace with real embedding-based dedup once there's an actual bank worth deduplicating against (Phase 3.5+).

## D-020 — Independent verifiers (reverification, judge) receive a narrow, explicitly-allowlisted view of a candidate — never the full object
**Status:** Accepted
**Context:** [PHASE_REVIEW.md](PHASE_REVIEW.md) §9.2 flagged that, while the Phase 3 reverification call happened not to leak the answer (it was passed only `candidate.stem`, a bare string), there was no structural guarantee against future leakage — a later change that passed the full `candidate` object, or added a field to it, could silently start leaking `correctAnswer`/`explanation`/`groundTruthDerivation`/`reasoning`/`solutionSteps` to a call that's supposed to be blind to them. Separately, the judge prompt DID pass `candidate.correctAnswer` labeled "claimed correct answer," which risked anchoring the judge toward confirming it rather than independently assessing the question.
**Decision:** `PresentedQuestionView` (`{ stem, options, answerFormat }`) and `JudgeView` (adds only `claimedDifficultyTier`) in `@ipmat/question-engine/src/verifierView.ts` are the ONLY types `buildReverificationUserPrompt()`/`buildJudgeUserPrompt()` accept, built via explicit field-by-field destructuring (never object spread of the candidate). The judge prompt no longer includes the candidate's claimed answer or explanation at all — it must independently determine whether the question has exactly one defensible answer among the options shown.
**Consequences:** Leakage is now prevented by the type system, not by prompt-authoring discipline — a future field added to `QuestionCandidateAiOutput` cannot leak through these two functions without a deliberate code change to the narrow view types themselves. Tested directly: a candidate fixture with marker strings planted in every field the verifier must not see, asserting those markers never appear in the built prompts (`test/verifierView.test.ts`).

## D-021 — Difficulty dimensions are explicitly marked `provisional`, never presented as calibrated
**Status:** Accepted
**Context:** [PHASE_REVIEW.md](PHASE_REVIEW.md) §8.2 and §9 named `buildBlueprintFromCell`'s `tierBaselineDimensions()` — a linear formula scaling a hand-picked baseline by tier index — as an unvalidated placeholder that could be mistaken for real calibration if nothing said otherwise.
**Decision:** `QuestionBlueprint` gained `difficultyCalibrationStatus: "provisional" | "expert_reviewed" | "empirically_calibrated"`, always `"provisional"` from `buildBlueprintFromCell()` today. No attempt was made to build a more "scientific-looking" formula — Phase 3.1 §4 explicitly asked not to, since a better-looking formula would still not be calibrated data and would only make the gap harder to notice.
**Decision, not done:** Real calibration needs actual student-attempt data (Phase 5+) and/or expert review — neither exists yet, and none was invented to fill the gap.
**Consequences:** Any code path that reads `difficultyDimensions` off a blueprint can also check `difficultyCalibrationStatus` and must not present those numbers as measured fact to a reviewer or student.

## D-022 — Blueprint compliance checking covers every field a candidate could drift on, not just concept and pattern family
**Status:** Accepted
**Context:** [PHASE_REVIEW.md](PHASE_REVIEW.md) noted (implicitly, via the pipeline's own scope) that `validateBlueprintCompliance()` originally checked only `blueprintId`, `conceptName`, and `patternFamilyName` — a candidate that silently claimed a different difficulty tier, dropped a required testing mode, built in the wrong trap, or combined with an unspecified concept would have passed.
**Decision:** `BlueprintExpectation` (`@ipmat/validation`) now also carries `difficultyTier`, `requiredTestingModes`, `trapErrorTaxonomyCode`, and `combinationConcepts`; `validateBlueprintCompliance()` checks all of them, each producing its own itemized `blueprint_violation` issue with a distinct `field` value. `exam`/`section`/`chapter` need no runtime check — the candidate schema has no field for them, so the AI is structurally unable to restate or change them.
**Consequences:** Five new deterministic rejection-path fixtures and tests (difficulty tier, testing mode, trap, and combination-concept violations, alongside the existing pattern-family violation) prove each check independently.

## D-023 — Examiner Lens comparison distinguishes four combination categories, not two
**Status:** Accepted
**Context:** [PHASE_REVIEW.md](PHASE_REVIEW.md) §9.7 flagged that `buildLensComparisonReport()`'s `supportedByGraph` check was type-blind — an AI proposal matching a `related_but_distinct` edge (which exists specifically to say "these look similar but do not combine them") would have counted as "supported," the same as a genuinely combinable edge.
**Decision:** The report now reports `validGenerationCombination` (a real, `commonly_combined`/`application`/`dependent` edge marked `usefulForQuestionGeneration: true`), `relatedButNonCombinable` (a real edge exists, but not a generation-useful type), `unsupportedByGraph` (no edge at all — invented), and `missedByAi` (a real, useful edge the AI never proposed) as four separate, mutually exclusive sets.
**Consequences:** The Percentages AI-Lens fixture now includes a proposal for "Probability" specifically to exercise the new `relatedButNonCombinable` category — the AI's fictional rationale ("both are numbers between 0 and 100") is the exact surface-level confusion the human Lens's `related_but_distinct` edge already warns about, which is a realistic failure mode this fix now correctly classifies instead of miscounting as support.

## D-024 — Fail closed on an unparseable `correctAnswer`, never silently skip its verification
**Status:** Accepted
**Context:** [PHASE_REVIEW.md](PHASE_REVIEW.md) §8.6/§9.6 flagged that `verifyComputation()`'s `parseNumeric()` returning `null` for an unparseable answer caused the `correctAnswer` cross-check to be silently skipped — a candidate could pass verification despite its stated answer never actually being checked. Worse, `Number("")` coerces to `0`, so an empty `correctAnswer` would have silently "matched" a computed value of 0.
**Decision:** A `correctAnswer` that fails to parse as a plain number now returns `fail("unverifiable_answer", ...)` — a hard rejection, not a skip. `parseNumeric()` also now explicitly regex-validates the cleaned string shape (rejecting `""` outright) rather than relying on `Number()`'s coercion quirks, and supports the common legitimate formats this project's questions actually use (₹/$/Rs. prefix, comma thousands separators, trailing `%`) without attempting fractions, ranges, or other formats (Phase 3.1 §3 explicitly asked not to over-engineer this).
**Consequences:** A candidate whose answer format this project doesn't yet support is now rejected rather than silently passed — a stricter, safer default. Widening supported formats is additive future work, not a redesign.

## D-025 — `runGenerationPipeline()` requires validated, explicit limits before making any AI call, and stops on budget overrun mid-run
**Status:** Accepted
**Context:** Phase 3.1 §9 required the generation infrastructure to have explicit limits (blueprint count, candidates per blueprint, retries, total attempts, estimated budget) before any batch generator is built — so that when one is built later, it inherits enforcement that already exists and is tested, rather than bolting safety on after the fact.
**Decision:** `GenerationLimits` (`@ipmat/question-engine/src/generationLimits.ts`) is validated by `validateGenerationLimits()` — thrown, listing every violated rule, before `runGenerationPipeline()` makes its first AI call. The pipeline also tracks running `estimatedCostUsd` across its own 3 calls and skips any remaining call (marking it `fail("budget_exceeded", ...)`) once the running total exceeds `maxEstimatedBudgetUsd` — proven with a mock provider that reports an artificially large token count.
**Consequences:** `DEFAULT_SINGLE_RUN_LIMITS` (1 blueprint, 1 candidate, $1.00 budget) is deliberately tight for a proof-of-concept; a future batch orchestrator must construct and pass its own `GenerationLimits`, and cannot bypass validation — there is no code path in `runGenerationPipeline()` that skips the check.

## D-026 — `@ipmat/ai`'s `generateStructured` schema parameter type was wrong for any schema using `.default()`
**Status:** Accepted (bug fix)
**Context:** Building the real-provider smoke test script (Phase 3.1 §5) surfaced a genuine type-signature bug: `GenerateStructuredInput<T>.schema` was typed `ZodSchema<T>`, which is `ZodType<T, ZodTypeDef, T>` — it forces the schema's Input type to equal its Output type. `examinerLensAnalysisAiSchema`'s `suggestedCombinations` field uses `.default([])`, making its Input type (`{...}[] | undefined`) legitimately differ from its Output type (`{...}[]`). No existing test caught this because no existing test called `generateStructured` with that specific schema and an explicit type parameter — the FixtureProvider-based tests all let TypeScript infer `T` from context in a way that happened not to trigger the mismatch.
**Decision:** Changed the field to `schema: ZodType<T, any, any>` — constraining only the Output type (T), which is the only one `generateStructured` actually uses (it consumes `schema.safeParse(...).data`, never the pre-parse input shape).
**Consequences:** This was a real bug that could have blocked the Examiner Lens regeneration task specifically (the one task schema using `.default()`) the first time anyone tried to call it with an explicit type parameter — exactly what building the real smoke test did. Found and fixed before any real API call was attempted, not after.

## D-027 — The generation pipeline fails closed, before any AI call, when the provider's model has no known pricing entry
**Status:** Accepted
**Context:** [PHASE_3_1_CODE_REVIEW.md](PHASE_3_1_CODE_REVIEW.md) §6 found the single most consequential gap in that review: `runGenerationPipeline()`'s `trackCost()` only incremented `runningCostUsd` when `metadata.estimatedCostUsd` was non-null. `estimateCostUsd()` (`@ipmat/ai`) returns `null` — not `0` — for any model absent from its hand-maintained pricing table. That meant an unrecognized model silently disabled the ENTIRE budget circuit breaker: `runningCostUsd` would never advance no matter how much was actually spent, and `overBudget()` could never return `true`.
**Decision:** Since every AI call inside one `runGenerationPipeline()` invocation uses the same `input.aiProvider` (and therefore the same `model`), pricing is knowable BEFORE any call is made, not just discoverable after one completes. A new `isKnownModel()` export (`@ipmat/ai/src/costEstimation.ts`) is checked immediately after `validateGenerationLimits()`, before the first (generation) call: if the model has no pricing entry, the pipeline refuses to run at all, returning a `rejected` result with a new `unverifiable_cost` rejection code on every check, and metadata showing no call was ever made. This also means every single invocation with an unknown model is blocked identically — there is no scenario where an unpriced model can make even one paid call under this pipeline.
**Consequences:** `trackCost()` was also tightened to check `metadata.estimatedCostUsd !== null` explicitly rather than a truthy check, as defense in depth — though with the pre-flight guard in place, a call that actually runs should never report a null cost in practice, since its model was already verified priced. Proven in tests with three separate cases: a known model's cost increments correctly across a full run; an unknown model never makes a single AI call; and five repeated invocations against an unknown model each fail closed identically, none of them ever spending.

## D-028 — Arithmetic verifier grammar narrowed further: comma removed, explicit length/magnitude/complexity bounds added
**Status:** Accepted (supersedes D-018's allowlist definition)
**Context:** [PHASE_3_1_CODE_REVIEW.md](PHASE_3_1_CODE_REVIEW.md) §2 found two real gaps in `verifyComputation()`'s arithmetic allowlist: (1) the allowlist included `,`, on the assumption it supported thousands-separator input, but mathjs's `evaluate()` treats a top-level comma as a STATEMENT separator, not a grouping character — `"1,000"` was never actually read as the number 1000, so the character served no real documented purpose and risked an expression silently evaluating as a multi-statement sequence; (2) there was no bound on a computation string's length, a numeric literal's magnitude, exponentiation complexity, or the final result's magnitude — a pathological string like a 24-digit number raised to another large number would pass the charset check and reach `evaluate()` uncapped.
**Decision:** `SAFE_ARITHMETIC_PATTERN` no longer permits `,` — the supported grammar is exactly digits, whitespace, `.`, and `+ - * / ^ ( )`. Four new, independent, pre-evaluation checks were added, each rejecting with `impossible_computation` before `evaluate()` is ever called: a 200-character length cap, a 15-digit cap per numeric literal, a 3-operator cap on `^` (chained/tower exponentiation is the primary way a short, charset-legal string can still be computationally explosive), and — post-evaluation — a `1e12` magnitude cap on the result, since no legitimate Percentages-chapter answer is anywhere near that large.
**Consequences:** `verifyComputation()` remains a deliberately narrow arithmetic verifier, not a general-purpose math parser — expanding the grammar (scientific notation, functions, comma-formatted numbers) stays a deliberate future decision (unchanged from D-018), now with the comma's non-function made explicit rather than left as a plausible-looking but nonfunctional inclusion. All four new bounds are independently tested, alongside a `comma` case proving the removed character is now rejected outright.

## D-029 — A deterministic, narrow guard against the generated stem leaking its own answer or internal metadata — explicitly not semantic leakage detection
**Status:** Accepted
**Context:** [PHASE_3_1_CODE_REVIEW.md](PHASE_3_1_CODE_REVIEW.md) §1 found that the `PresentedQuestionView`/`JudgeView` leakage boundary (D-020) protects against the STRUCTURED fields of a candidate leaking to the independent verifiers, but does nothing about the free-text `stem` itself stating its own answer — since the stem is, correctly, included in both views (the verifiers must be able to see the actual question). A poorly-generated stem could embed the answer directly ("...the original price was 480. What was...") and no existing check would catch it.
**Decision:** A new `validateNoAnswerLeakageInStem()` (`@ipmat/validation/src/qualityValidators.ts`), wired into `validateCandidateStructurally()`, checks two concrete, deterministic, whole-token/phrase substring conditions: the claimed `correctAnswer` must not appear verbatim in the stem, and the internal `blueprintId` must never appear in the stem at all. Explicitly rejected: a keyword blacklist attempting to guess at leakage phrasing — the task instructions for this phase (Phase 3.1.1 §3) specifically asked not to build one, since it would create a false impression of semantic understanding this codebase does not have.
**Consequences:** This is documented, in the function's own doc comment and here, as NOT semantic leakage detection — it cannot catch a paraphrased leak (the numeral leaked as words), an algebraically-derivable leak, or a leak via a different phrasing. It also carries a known, accepted false-positive risk for short/common correct-answer values that coincidentally match an unrelated given quantity in the stem (mitigated, not eliminated, by requiring whole-token matches and skipping answers under 2 characters). A pass from this check must be read as "no verbatim leak of this specific, checkable kind was found," never as "the stem provably does not leak the answer."

## D-030 — Examiner Lens comparison matches AI-proposed concept names by normalized key, not raw string equality — exact match only, never fuzzy
**Status:** Accepted
**Context:** [PHASE_3_1_CODE_REVIEW.md](PHASE_3_1_CODE_REVIEW.md) §5 found that `buildLensComparisonReport()`'s combination categorization used case-sensitive, whitespace-sensitive `Set` lookups against AI-proposed concept names — a real model returning "ratio" instead of "Ratio," or with incidental leading/trailing whitespace, would be reported as an INVENTED relationship (`unsupportedByGraph`) purely due to formatting, undermining the credibility of a report whose entire purpose is catching genuine AI overclaiming.
**Decision:** A new `normalizeConceptNameKey()` (`@ipmat/concept-graph/src/graph.ts`) — trim, collapse internal whitespace runs, lowercase — is used to build normalized-key lookup maps for both the "valid generation combination" and "related but non-combinable" concept sets; an AI-proposed name is matched against these maps by its own normalized key, and on a match is reported under the graph's CANONICAL spelling, not the AI's raw string. This is deliberately narrow: no stemming, no pluralization folding, no fuzzy/typo correction. "Percentage" and "Percentages" normalize to two DIFFERENT keys and are never treated as the same concept — an unrecognized or misspelled name still correctly falls through to `unsupportedByGraph` rather than being silently mapped to whatever concept it looks closest to.
**Consequences:** Same discipline as every other "narrow, exact, never guess" decision in this log (D-018, D-024, D-028, D-029) — normalization closes a real false-positive gap without introducing a new false-negative one. Tested directly against name variants (lowercase, all-caps, stray whitespace) for both the valid and related-but-non-combinable categories, and against a genuinely unsupported name with whitespace variance to prove normalization never invents a match for a name that was never real.

## D-031 — The `AnthropicProvider` output-token cap and the generation pipeline's cost-safety assumptions are now one documented, tested coupling
**Status:** Accepted
**Context:** [PHASE_3_1_CODE_REVIEW.md](PHASE_3_1_CODE_REVIEW.md) §6/§10 found that the real bound on a single AI call's worst-case cost was `AnthropicProvider`'s hardcoded `max_tokens: 4096` — a fact `generationLimits.ts`'s reactive (checked-between-calls) budget breaker depends on being true, but which neither file referenced or enforced. A future change to either file in isolation (raising the output cap, or adding a pricier default model) could silently reintroduce a much larger single-call blast radius than the budget breaker's own design assumes.
**Decision:** The constant is now named and exported (`ANTHROPIC_MAX_OUTPUT_TOKENS_PER_CALL`, `@ipmat/ai`), with a doc comment cross-referencing this decision and the function that depends on it. `worstCaseSingleCallCostUsd()` (`@ipmat/question-engine/src/generationLimits.ts`) imports that exact constant and `estimateCostUsd()` to compute, for any model, the worst-case cost of ONE call at that output cap and a documented, conservative assumed input-token ceiling (`ASSUMED_MAX_PROMPT_INPUT_TOKENS = 2000` — generous relative to what this codebase's own prompt construction actually produces). This is the one place the coupling is made explicit, and it is tested: a regression test asserts this worst-case bound stays under `DEFAULT_SINGLE_RUN_LIMITS.maxEstimatedBudgetUsd` for every currently priced model, so a future change that breaks the assumption fails a test rather than silently drifting.
**Consequences (explicitly NOT claimed):** This bounds a SINGLE call's worst case, not a full pipeline run's aggregate (three calls). Because the budget check is reactive, a full run's actual worst-case spend can still exceed `maxEstimatedBudgetUsd` by up to roughly one more call's worst-case cost before the breaker stops the next one — this is a real, bounded (not unbounded) property, not eliminated by this decision, and no production billing guarantee is implied by any of this — see the "reactive, not predictive" limitation already recorded in [PHASE_3_1_REVIEW.md](PHASE_3_1_REVIEW.md) §11.

## D-032 — The generation system prompt explicitly lists every field blueprint compliance enforces; the deterministic validator remains authoritative regardless
**Status:** Accepted
**Context:** [PHASE_3_1_CODE_REVIEW.md](PHASE_3_1_CODE_REVIEW.md) §8 found that `validateBlueprintCompliance()` (D-022) enforces 7 fields a candidate must not drift on, but `buildGenerationSystemPrompt()`'s explicit "you MUST NOT change X" framing only named 3 of them (concept, pattern family, target skill) — the model was never explicitly told not to alter difficulty tier, testing modes, the trap, or the combination-concept set, even though drifting on any of those is deterministically rejected. This is a quality/efficiency gap (avoidable rejections), not a safety gap (the validator already caught every case).
**Decision:** `buildGenerationSystemPrompt()` now explicitly enumerates all 7 fields in its "MUST NOT change" instruction, and the stem-leakage expectation (D-029) is also stated directly in the prompt. The deterministic validator was NOT relaxed or changed to accommodate the prompt in any way — the prompt update is purely about giving the model a fair, complete statement of the rule it is already being held to.
**Consequences:** No behavior change to what is accepted or rejected; this should reduce the rate of blueprint-violation and answer-leakage rejections once exercised against a real model, but that is an expectation, not a measured result — no real model has been run yet (see [PHASE_3_1_1_REVIEW.md](PHASE_3_1_1_REVIEW.md) §7).

## D-033 — `distractor_quality` kept as a real check, given a dedicated fixture and test, rather than removed as dead code
**Status:** Accepted
**Context:** [PHASE_3_1_CODE_REVIEW.md](PHASE_3_1_CODE_REVIEW.md) §3 found that `validateSingleCorrectAnswer()`'s duplicate-distractor branch (`distractor_quality`) was unreachable by every existing test — the one fixture with duplicate options also duplicated the CORRECT answer, so the function always returned on the `multiple_or_no_correct_answer` check first, before ever reaching the distractor-uniqueness check.
**Decision:** Duplicate wrong-answer options are a genuine, distinct question-quality defect (two distractors so similar they're identical text is a real authoring failure, independent of whether the correct answer itself is fine) — the branch was kept, not removed, and given a dedicated fixture (`duplicateDistractorCandidate`: a unique correct answer among options, with two of the WRONG options identical) and a test proving it fires `distractor_quality`, not `multiple_or_no_correct_answer`.
**Consequences:** The smallest-scope fix available: no logic changed, only test coverage added, closing the "misleading dead validation logic" gap the review named without touching behavior that was already correct.

## D-034 — Attempt lifecycle: one finalization funnel, structurally forgery-immune correctness/timing, canonical event vocabulary
**Status:** Accepted
**Context:** Phase 1's `Attempt`/`AttemptEvent` schema existed but nothing wrote or read it yet (docs/MASTER_PLAN.md Phase 1: "these tables simply exist, empty"). Phase 4A is the first phase to implement the actual state machine, and the phase brief was explicit: never trust a client-calculated `isCorrect` or `timeTaken`, and fail closed on every invalid transition.
**Decision:**
- A new `AttemptStatus` enum (`in_progress | submitted | skipped | abandoned`) and `attempts.status`/`attempts.finalized_at` columns (migration `0003_attempt_lifecycle`). `in_progress` is the only non-terminal state.
- `AttemptEventType` is renamed to a canonical vocabulary (`question_opened`, `answer_selected`, `answer_changed`, `hint_opened`, `solution_opened`, `question_skipped`, `answer_submitted`, plus the pre-existing `working_input_changed`/`reasoning_submitted` reserved for Phase 5) — safe because no environment has ever applied a migration against a live database (same reasoning as every prior schema rename in this log).
- A new, database-free domain package `packages/domain/attempt` implements `startAttempt()`, `recordAttemptEvent()`, `submitAttempt()`, `skipAttempt()`, and `finalizeAttempt()` as pure functions over an in-memory `AttemptState` (never mutating their input — the same discipline `applyCatchUp()` uses for `PrepPhaseTemplate`).
- **Correctness and time-taken are structurally, not just behaviorally, forgery-immune:** `submitAttempt()`'s signature has no parameter through which a caller could pass `isCorrect` or a duration — `chosenAnswer` is derived from the LAST `answer_selected`/`answer_changed` event already recorded on the attempt, `isCorrect` is computed fresh by comparing it to the authoritative `AttemptQuestionContext.correctAnswer` passed in by the caller, and `timeSpentSeconds` is always `finalizedAt - startedAt` using timestamps the domain layer itself validates for coherence. There is no code path, public or private, that accepts a pre-computed correctness flag or duration and stores it as-is.
- `question_skipped` and `answer_submitted` are excluded from `RecordableAttemptEventInput` (the type `recordAttemptEvent()` accepts) at the TYPE level — only `submitAttempt()`/`skipAttempt()` can ever append those two event types, as part of the same operation that transitions `status`. A caller cannot fire a "submit" event through the generic recording path while bypassing the validation that's supposed to accompany an actual submission.
- Every invalid-transition/malformed-input case throws a typed `AttemptLifecycleError` with a specific `code` (`attempt_not_found`, `already_finalized`, `ownership_mismatch`, `malformed_event_payload`, `impossible_timestamp`, `missing_answer`, `invalid_answer_option`) — deliberately NOT `@ipmat/validation`'s `ValidationResult` pattern, since an attempt lifecycle violation is a precondition/trust error to fail fast on, not a diagnostic quality signal to collect alongside other passing checks (unlike AI-candidate rejection reasons, which are meant to all be reported together).
**Consequences:** A future persistence adapter (Prisma-backed, not built this phase — no live database has ever been reachable) is responsible for loading an `AttemptState` from `attempts`/`attempt_events` rows before calling into this package and persisting the result afterward; "cannot submit a nonexistent attempt" is enforced today only as a null/undefined guard at this pure-domain layer, not as a real database lookup, which is an honest, documented limitation until that adapter exists.

## D-035 — Skip is a terminal transition; answer-change history and the Autopsy/Mastery evidence contracts are derived projections, never stored columns
**Status:** Accepted
**Context:** Phase 4A §6 asked for a clearly defined state machine that prevents invalid transitions, explicitly leaving "is submit-after-skip allowed?" as a design decision for this phase to make (not a given requirement). Separately, §4/§9/§10 asked for answer-change tracking and Autopsy/Mastery data contracts without specifying whether they're new stored fields or computed views.
**Decision:** Skip is modeled as a full terminal state, equal in finality to submit and abandon — once `skipAttempt()` returns, the attempt's `status` is `"skipped"` and any further `submitAttempt()`/`skipAttempt()`/`recordAttemptEvent()` call throws `already_finalized`. This is the simplest, safest interpretation consistent with "prevent invalid transitions" and matches how `submitted`/`abandoned` already behave — there was no product requirement demanding skip be reversible, and making it reversible would have meant a fourth, more complex family of transition rules for no stated benefit. Separately: `deriveAnswerChangeHistory()` (initial/final answer, change count, full sequence), `toAutopsyEvidence()`, and `toMasteryContribution()` are all pure functions computed from an `AttemptState`'s existing `events`/fields on every call — none of them are new Prisma columns, following the same "derive, don't cache" discipline as `MasteryState`, pattern-family coverage, and Examiner Lens combinations (docs/DECISIONS.md D-015).
**Consequences:** If a future phase decides skip SHOULD be reversible (e.g., "come back to a skipped question later in the same session"), that is a new, explicit state-machine change to make deliberately, not a bug to fix — this decision record is the place to note that reversal, superseding this entry, rather than quietly patching `skipAttempt()`. The Autopsy/Mastery contract types (`AttemptAutopsyEvidence`, `AttemptMasteryContribution`) are intentionally minimal and structurally cannot express confidence, motivation, intelligence, or emotion (docs/DECISIONS.md D-005, D-006) — no field for any of them exists, by design, not by omission.

## D-036 — A new `@ipmat/autopsy` package implements OBSERVATION -> EVIDENCE only; deterministic, no AI, candidate error is structurally distinct from confirmed error
**Status:** Accepted
**Context:** Phase 5A's brief named a four-layer model — OBSERVATION -> EVIDENCE -> HYPOTHESIS -> CONFIRMED DIAGNOSIS — and was explicit that only the first two are in scope this phase, and that nothing may infer confidence, motivation, emotion, intelligence, anxiety, laziness, carelessness, or intent from behavior alone. `@ipmat/attempt`'s `AttemptAutopsyEvidence` (Phase 4A, D-034) already provides OBSERVATION; nothing yet turned it, plus the authoritative Question DNA and the existing `ErrorTaxonomy`, into structured EVIDENCE.
**Decision:** A new, database-free domain package `packages/domain/autopsy` (`@ipmat/autopsy`) adds:
- `AutopsyQuestionContext` — restated Question DNA fields (exam/section/chapter/concept/pattern family/taxonomy cell/difficulty tier & dimensions/novelty level/exam relevance/testing modes/trap code/combined concepts), deliberately WITHOUT `expectedTimeSeconds` — that field already lives on `AttemptAutopsyEvidence`, and repeating it would be exactly the unnecessary duplication the phase brief warned against.
- `deriveBehaviorSignals()` — deterministic booleans (`correctFast`/`correctSlow`/`incorrectFast`/`incorrectSlow`/`answerChanged`/`multipleAnswerChanges`/`hintUsed`/`solutionOpened`/`skipped`/`noAnswer`/`timeAboveExpected`/`timeBelowExpected`) plus `speedRatio` (`timeTaken / expectedTime`, computed ONLY when both are present, finite, and `expectedTime > 0` — never manufactured otherwise). All thresholds (`FAST_SPEED_RATIO`, `SLOW_SPEED_RATIO`, `MULTIPLE_ANSWER_CHANGES`, `REPEATED_EVIDENCE_MIN_COUNT`) are centralized named constants in `AUTOPSY_THRESHOLDS`, never scattered magic numbers.
- `deriveHintSolutionEvidence()` — genuine event-order comparison (hint/solution event index vs. the terminal event's index in the timeline), not an assumed value, even though it is currently always true whenever both exist (a direct consequence of Phase 4A's "no event after finalization" guarantee) — computed for real so it stays correct if that guarantee ever changes.
- `deriveHistoricalSignals()` — purely observable repetition COUNTS (same concept/pattern-family/taxonomy-cell failure, repeated slow/hint/solution/novelty/pressure patterns) across the current attempt plus caller-supplied prior attempts, each count naming the exact attempt ids that contributed. Returns `null` entirely (not a zero-filled struct) when no prior attempts were supplied, and any individual count stays `null` until it reaches `REPEATED_EVIDENCE_MIN_COUNT` (2) — a single occurrence is never "repeated."
- `deriveCandidateErrorEvidence()` — a deterministic pattern match between an incorrect attempt and the question's own designated trap code against the EXISTING `ErrorTaxonomy` (a restated `ErrorTaxonomyEntry` shape, caller-supplied — this package cannot depend on `@ipmat/db`, so it does not import the real seed data, but uses the identical entries as a fixture; no second, competing taxonomy is created). The result type, `CandidateErrorEvidence`, has NO `confirmed` field anywhere and always carries a mandatory `qualification` string stating plainly that it is a candidate, not a confirmed diagnosis.
- `buildAutopsyOutput()` — the single orchestrator producing a fully-typed `AutopsyOutput` (`attemptFacts` reused directly from `@ipmat/attempt`, `questionFacts`, `behaviorSignals`, `hintSolutionEvidence`, `historicalSignals | null`, `candidateErrorEvidence | null`, `availableEvidence`/`missingEvidence` string lists). Every function in this package is pure — none mutates its input, matching the discipline already established for `applyCatchUp`/`@ipmat/attempt`'s lifecycle functions.
**Consequences:** `AutopsyHypothesis` (the HYPOTHESIS layer) is defined as a TYPE ONLY in this same package, with no function anywhere that constructs one — Phase 5B must build the actual AI call. `candidateErrorCategory`/`candidateErrorTaxonomyCode` (evidence) and `proposedErrorCategory`/`confirmed` (a future hypothesis/the real `Autopsy.confirmed` column) remain structurally distinct types with different names, precisely so a future implementer cannot accidentally treat a candidate as if it were confirmed just because the field names happened to line up. **Update (Phase 5B, D-038):** this consequence is now historical, not current — `AutopsyHypothesis` is implemented (`generateHypothesis()`, `hypothesis.ts`), and the type-name separation described above held up exactly as intended once that implementation landed.

## D-037 — `RepairContext` gets a real deterministic builder; `AutopsyHypothesis` deliberately does not
**Status:** Accepted
**Context:** Phase 5A §10 said "do NOT generate hypotheses" (full stop) while §11 said "define a minimal future RepairPlan input contract that CAN IDENTIFY" a target concept/pattern/cell/candidate-category/training-mode/priority — different verbs, suggesting different scope. Explaining why one contract ships with code and the other doesn't matters enough to record, so a future reader doesn't assume the asymmetry was accidental.
**Decision:** `buildRepairContext(output: AutopsyOutput): RepairContext` IS implemented — it is a simple, deterministic, rule-based summary of evidence `buildAutopsyOutput()` already computed (repeated-failure patterns -> `priority: "high"`; a lone candidate error -> `"medium"`; repeated pressure/novelty difficulty -> a specific `recommendedTrainingMode`), not a new inference. It explicitly does NOT select or generate actual follow-up questions — `RepairContext` has no `followUpQuestionIds` field at all, tested directly. `AutopsyHypothesis`, by contrast, has NO builder function anywhere in this package — proposing an explanation for WHY a student got something wrong requires actually reading and reasoning about the specific question/attempt in natural-language terms, which this phase's explicit "do NOT call an LLM" constraint puts out of reach; defining the type without a function is the honest way to say "the shape is ready, the reasoning is not built."
**Consequences:** `RecommendedTrainingMode`'s vocabulary (`standard_practice`/`guided_hint_first`/`timed_pressure_drill`/`novelty_exposure`) is explicitly marked provisional in its own doc comment — a v1 heuristic, expected to grow deliberately the same way `ErrorTaxonomy` itself does (docs/DATABASE.md §Error Taxonomy), not a finalized taxonomy. `RepairPriority` (`low`/`medium`/`high`) is a plain rule-based label, not a claim about urgency grounded in anything beyond the repetition counts and candidate-error presence already in `AutopsyOutput`.
**Update (Phase 5B, D-038):** the "`AutopsyHypothesis` deliberately does not [have a builder]" half of this decision describes Phase 5A only — Phase 5A's own explicit "do NOT call an LLM" constraint, which was the actual reason for the asymmetry. Phase 5B lifted that constraint and built `generateHypothesis()`, so `AutopsyHypothesis` now has a real builder too. The REASONING recorded here (why the asymmetry existed, and that it was deliberate, not an oversight) remains an accurate historical record of Phase 5A's decision; only the "still true today" reading of "does not" is superseded.

## D-038 — Hypothesis generation is a 5th `@ipmat/ai` task; confirmation is one shared state-transition function; a hypothesis can reach "confirmed" only through an explicit student action
**Status:** Accepted (evolves D-036's originally type-only `AutopsyHypothesis`)
**Context:** Phase 5A deliberately left `AutopsyHypothesis` unimplemented — a contract, not code. Phase 5B's job is to build the real thing: an AI call that proposes ONE hypothesis from Phase 5A's deterministic `AutopsyOutput`, and a deterministic domain model for the student's response to it. The phase brief was explicit that a hypothesis must never auto-promote to a diagnosis, and that "model confidence" (for ranking) must never be confused with, or exposed as, "student confidence."
**Decision:**
- `autopsyHypothesisAiSchema` (`@ipmat/ai/src/schemas/autopsyHypothesis.ts`) is the 5th task schema, following the same pattern as `examiner-lens-analysis`/`question-generation`/`answer-reverification`/`validation-judge` — restated vocabulary, zero dependency on domain packages (D-017). Its `modelConfidence` field is explicitly documented, in the schema itself and in the system prompt, as the MODEL's own confidence in one hypothesis, never the student's confidence in anything.
- `generateHypothesis()` (`@ipmat/autopsy/src/hypothesis.ts`) goes through `generateStructured()` like every other AI call in this codebase — no direct provider SDK call, output schema-validated and otherwise untrusted. It refuses to make any call at all (`no_evidence_to_diagnose`) when `AutopsyOutput.candidateErrorEvidence` is null (a correct/skipped/abandoned/in-progress attempt has nothing to diagnose) — the same "fail closed before spending" discipline `runGenerationPipeline()`'s unknown-model check already established (D-027). It ALWAYS returns a hypothesis with `confirmationStatus: "awaiting_confirmation"` — there is no code path, anywhere, that constructs one pre-confirmed.
- `applyConfirmationResponse()` is the single shared transition `confirmHypothesis()`/`rejectHypothesis()`/`correctHypothesis()` all funnel through (mirroring `@ipmat/attempt`'s `applyFinalization()` pattern, D-034) — it is the ONLY function that can move `confirmationStatus` away from `"awaiting_confirmation"`, and it refuses (`already_decided`) if called on an already-decided hypothesis. `"corrected"` is a distinct terminal status from `"rejected"`: the student's own replacement text (`studentCorrectionText`) is preserved as NEW evidence, never overwriting `proposedExplanation`.
**Consequences:** The system prompt (`hypothesisPrompts.ts`) instructs the model not to invent evidence, not to make psychological claims, and to phrase its explanation as a hypothesis — but a prompt instruction cannot structurally stop a model from ignoring it (tested directly: a fixture hypothesis that DOES make a forbidden claim is still schema-valid and is still wrapped into an `awaiting_confirmation` hypothesis, exactly because confirmation — not the model's good behavior — is what this codebase actually trusts). This is a real, accepted limitation of any prompt-based instruction, not something this decision claims to solve.

## D-039 — `RepairPlan` requires a CONFIRMED hypothesis specifically; Autopsy/RepairPlan persistence needs no schema change
**Status:** Accepted
**Context:** Phase 5A's `RepairContext` can be built from evidence alone, for any incorrect attempt — that's still true and unchanged. Phase 5B §6 asked for a `RepairPlan` that additionally identifies a target error category and prerequisites, built from a "confirmed diagnosis / confirmed error." Separately, §5 asked to inspect the existing `Autopsy`/`RepairPlan` Prisma tables and only migrate if genuinely required.
**Decision:** `buildRepairPlan(hypothesis, output, {graph?})` (`@ipmat/autopsy/src/repairPlan.ts`) throws `not_confirmed` unless `hypothesis.confirmationStatus === "confirmed"` — a `"corrected"` hypothesis is deliberately NOT accepted, because the student's free-text correction has no structured category to target without another (unbuilt) diagnosis pass. `targetErrorCategory` comes from the CONFIRMED hypothesis (the student-validated signal); `targetErrorTaxonomyCode` comes from the separately-computed, deterministic `candidateErrorEvidence` (Phase 5A) — these can legitimately differ (a documented, not hidden, tension: the AI-proposed category was confirmed, but the deterministic code-match is a different, unconfirmed mechanism). Prerequisites are resolved via `@ipmat/concept-graph`'s EXISTING `getPrerequisites()` when a graph is supplied, never a second lookup mechanism. Inspecting the existing schema found NO migration was needed for either table: `autopsies.confirmed: Boolean?` + `autopsies.student_correction_text: String?` already jointly encode all 4 `HypothesisConfirmationStatus` values (`null`/`null` = awaiting; `true`/`null` = confirmed; `false`/`null` = rejected; `false`/text = corrected — see `toAutopsyPersistenceRecord()`), and `repair_plans` already has everything a `RepairPlan` needs (`follow_up_question_ids` simply stays `[]`, since this package never selects questions).
**Consequences:** `toAutopsyPersistenceRecord()`/`toRepairPlanPersistenceRecord()` (`@ipmat/autopsy/src/persistence.ts`) are pure mapping functions only — nothing calls `prisma.autopsy.create()` or `prisma.repairPlan.create()` anywhere in this codebase; no persistence adapter exists, matching Phase 5B §5's "do not pretend persistence exists if no adapter is implemented."

## D-040 — Mastery Engine: multidimensional by construction, reuses `AutopsyQuestionContext` rather than a third Question DNA shape, needs one additive migration
**Status:** Accepted
**Context:** Phase 5B §7 required an actual `MasteryState` computation — multidimensional, never collapsed to one score — consuming many `AttemptMasteryContribution` records (Phase 4A). Those records alone carry no Question DNA (difficulty tier, novelty level, testing modes, pattern family), which every mastery dimension except raw accuracy needs. Phase 5A had already restated a Question-DNA-shaped type once (`AutopsyQuestionContext`) specifically because the fields it needed overlapped, but weren't identical to, `@ipmat/question-engine`'s full `QuestionDnaData`.
**Decision:** A new package, `packages/domain/mastery` (`@ipmat/mastery`), pairs each `AttemptMasteryContribution` with the SAME `AutopsyQuestionContext` type Phase 5A already defined (`MasteryAttemptRecord`) — reused directly via a dependency on `@ipmat/autopsy`, not restated a third time, closing exactly the "duplicated Question DNA" risk Phase 5B §18/§21 named explicitly. `buildComponentDetail()` (`componentDetail.ts`) is the ONE shared counting/statistics builder every aggregation grain (`computeMasteryState()` for concept, `computePatternFamilyMasteryDetail()`, `computeTaxonomyCellMasteryDetail()`) funnels through — no per-grain duplicate counting logic. Coverage reuses `@ipmat/question-engine`'s EXISTING `PatternFamilyCoverage`/`computePatternFamilyReadiness()` for CONTENT readiness (`coverage.contentCoverage`), kept explicitly distinct from `coverage.taxonomyCellsEncountered` (STUDENT exposure) — two different, both legitimate, measurements sharing one taxonomy vocabulary, not a second coverage model (Phase 5B §12/§18). The `mastery_states` table needed one additive column, `component_detail: Json` (migration `0004_mastery_component_detail`, generated the same schema-datamodel-diff way as every prior migration, NOT applied — no live database has ever been reachable) — the 5 existing scalar columns (`accuracy`/`speed_ratio`/`novelty_handling`/`pressure_performance`/`pattern_coverage`) are unchanged, per "use existing fields where possible."
**Consequences:** `@ipmat/mastery` has no dependency on `@ipmat/ai` in its own source (only its cross-package integration TEST does, to build a realistic fixture chain) — mastery computation is entirely deterministic and needs no AI call, matching Phase 5B §19.

## D-041 — A centralized, provisional observation-count gate replaces any composite "mastery score"; no recency/decay formula is implemented
**Status:** Accepted
**Context:** Phase 5B §9 forbade inventing fake scientifically-validated weights, and §10 forbade an unexplained recency-decay formula, while still asking for SOME way to distinguish "insufficient data" from a real measurement, and for the engine to be recency-ready later.
**Decision:** `MASTERY_CONSTANTS.MIN_OBSERVATIONS_FOR_COMPONENT` (currently 3) is the ONLY centralized, named constant in `@ipmat/mastery` — each of the 5 headline `MasteryComponentMeasures` (accuracy, speedRatio, noveltyHandling, pressurePerformance) is reported `null` below this many relevant observations, explicitly marked `PROVISIONAL` in its own doc comment (mirroring `difficultyCalibrationStatus: "provisional"`, D-021) rather than dressed up as calibrated. No composite/blended score is computed anywhere — each measure is a plain, unweighted ratio, preferring "component measures over arbitrary composite scores" exactly as instructed. Recency: NO decay/weighting is applied anywhere; `MasteryComponentDetail` instead preserves everything a future recency-aware pass would need without this phase inventing the weighting scheme itself — `contributingAttemptIds` in chronological order, `earliestAttemptAt`/`latestAttemptAt`, and `accuracyStability.sequence` (the raw, ordered 0/1 correctness sequence).
**Consequences:** `MIN_OBSERVATIONS_FOR_COMPONENT = 3` is a deliberately low, clearly-labeled placeholder, not validated against real student reliability data — raising or lowering it later is a config change, not a redesign, since every raw count it gates is independently preserved in `MasteryComponentDetail` regardless of what the gate decides for the headline measure.

## D-042 — `MasteryState` persistence writes nothing when any headline measure is insufficient-data, rather than coercing a misleading default
**Status:** Accepted
**Context:** The existing `mastery_states.accuracy`/`speed_ratio`/`novelty_handling`/`pressure_performance`/`pattern_coverage` columns are all non-nullable `Float`, but D-041 makes each of `@ipmat/mastery`'s corresponding domain measures legitimately `null` when there's insufficient data. Writing `0` in place of `null` would misrepresent "we don't know yet" as "0% mastery" — precisely the kind of misleading collapse Phase 5B was told to avoid.
**Decision:** `toMasteryStatePersistenceRecord()` (`@ipmat/mastery/src/persistence.ts`) returns `null` — write nothing — whenever ANY of the 5 headline measures is still `null`. This is a real, documented tension with the existing schema, deliberately not resolved by a schema change this phase (no persistence adapter is being built at all, so there is nothing yet to widen the columns for).
**Consequences:** A future persistence adapter will need its own policy decision here — likely either widening these 5 columns to nullable `Float`, or a smarter per-field write strategy (e.g. tracking "has this dimension ever had enough data" separately from the value itself) — recorded here as a known open question for whoever builds that adapter, not decided unilaterally in this phase.

## D-043 — `MasteryState` persistence: nullable `Float?` columns are the chosen representation for "measured vs insufficient-evidence vs zero"; the repository/adapter layer lives in `@ipmat/db`, not a new package or the domain packages themselves

**Status:** Accepted (resolves the open question D-042 left for "whoever builds that adapter" — Phase 5C-1 is that phase)
**Context:** Phase 5C-1 was asked to build the first real persistence/repository layer for Autopsy, RepairPlan, and MasteryState, and specifically to resolve D-042's open tension: distinguish **measured** / **insufficient evidence (unavailable)** / **zero** for each of the 5 `MasteryComponentMeasures`, without collapsing any two of those into each other, and without using "nullable database fields" as an unexamined shortcut.
**Decision:**
- **Representation:** the 5 `mastery_states` scalar columns (`accuracy`/`speed_ratio`/`novelty_handling`/`pressure_performance`/`pattern_coverage`) are widened to nullable `Float?` (migration `0005_mastery_state_nullable_measures`). SQL `NULL` means exactly what `MasteryComponentMeasures`'s `null` already means in the domain layer (insufficient data, D-041) — no translation happens at the persistence boundary. A real float, including `0.0`, means the dimension was measured; `null !== 0` at both the SQL and TypeScript level, so "zero" and "unknown" are never confused. A companion "is this measured" status column per field was considered and rejected: it would duplicate information `NULL` already carries unambiguously, and the domain model has no other reason a measure would be null (D-041's only null-producing case is the observation-count gate) — adding one would be exactly the kind of premature abstraction this codebase avoids. `componentDetail` (already `NOT NULL` `Json`, D-040) independently preserves the raw counts behind every gate, so "why is this dimension null" is always answerable from the same row without needing a second column to say so.
- **Row-level granularity changed, not just column nullability:** Phase 5B's `toMasteryStatePersistenceRecord()` returned `null` — wrote NOTHING — if ANY of the 5 measures was null (D-042). Phase 5C-1 changes this to a genuine three-state model at the ROW level too: the function now returns `null` (nothing written) ONLY when `detail.totalAttempts === 0` (mastery was never computed at all for this student/concept); once any attempt exists, a row IS written, with each of the 5 measures independently `null` or a real number on that same row. This was necessary, not optional — otherwise a student with plenty of `accuracy` data but no `pattern_coverage` context would still get nothing persisted at all, silently discarding real, usable data.
- **Repository placement:** the first repository/adapter code in this codebase (`AutopsyRepository`/`RepairPlanRepository`/`MasteryStateRepository`, `packages/db/src/repositories/`) lives in `@ipmat/db`, not a new package and not inside `@ipmat/autopsy`/`@ipmat/mastery`. This follows the EXISTING precedent docs/ARCHITECTURE.md §4 already names explicitly: "`/packages/db`'s seed script is the one place that imports domain-package fixtures and writes them through Prisma; this is the correct dependency direction." `@ipmat/db` gained `@ipmat/autopsy`/`@ipmat/mastery` as new dependencies (infra depending on domain, never the reverse) and now exposes `main`/`types` so a future `apps/web` can import these repositories directly. Each repository is a plain interface (the "contract," e.g. `MasteryStateRepository`) plus exactly one concrete `PrismaXRepository` implementation — there is deliberately no dependency-injection framework or second abstraction layer.
- **Testing without a live database:** since no environment has ever had a reachable database (docs/MASTER_PLAN.md "Current state"), `PrismaXRepository` classes are typechecked against the real generated Prisma Client types but never executed in tests. Round-trip persistence semantics (save → find, upsert idempotency, rejection of invalid state) are instead verified against `InMemoryXRepository` test doubles (`packages/db/test/fixtures/inMemoryRepositories.ts`) implementing the identical interface and reusing the SAME validation logic (`PersistenceError`, `HypothesisError`) the Prisma-backed classes use — this tests the CONTRACT's semantics honestly, not a mocked-out illusion of persistence.
- **Foreign-key resolution is the repository's job, not the domain layer's:** `toAutopsyPersistenceRecord()`/`toRepairPlanPersistenceRecord()`/`toMasteryStatePersistenceRecord()` are unchanged in this respect (still pure, still take resolved ids as parameters) — `PrismaAutopsyRepository`/`PrismaRepairPlanRepository` resolve `ErrorTaxonomy.code -> id` and `Concept.name -> id` via `findUnique`/`findFirst` before calling them. `Concept.name` resolution is a deliberately narrow, name-only lookup (real schema uniqueness is `[chapterId, name]`) — an honest simplification scoped to this single-chapter vertical slice, flagged in code for revisit if a second chapter is ever built.
- **New defensive layer, distinct from existing domain errors:** `PersistenceError` (`packages/db/src/repositories/errors.ts`) is a new typed error class for "this data is not safe to write" (malformed/empty ids, non-finite numeric measures) — deliberately separate from `HypothesisError`/`AttemptLifecycleError`, which represent domain-rule violations the domain packages already guard on their own terms before persistence is ever reached.
**Consequences:** `PrismaAutopsyRepository.save()` also re-checks `hypothesis.attemptId === output.attemptFacts.attemptId` (reusing `HypothesisError("mismatched_attempt", ...)`, a code that already existed in `HYPOTHESIS_ERROR_CODES` but had no caller before this phase) — belt-and-suspenders defense at the persistence boundary, not a claim that the domain layer's own guarantees are insufficient. An automated test (`packages/db/test/architecture/domainBoundary.test.ts`) now scans every `packages/domain/*` package's `package.json` and source files for a `@prisma/client`/`@ipmat/db` import, turning docs/ARCHITECTURE.md §6's dependency-direction rule into something CI can actually fail on, not just a convention.

## D-044 — Repair Selection (Phase 5C-2) is a deterministic, explicit-tier match against a confirmed `RepairPlan` — never an opaque "AI picks the question" step, and explicitly NOT the adaptive engine

**Status:** Accepted
**Context:** Phase 5B's `RepairPlan` deliberately stops at identifying a target (concept, pattern family, taxonomy cell, error category, training mode) — it has no `followUpQuestionIds` field, and Phase 5B explicitly left actual question selection to a later phase. Phase 5C-2 is that phase's TARGETED half: given one confirmed diagnosis, pick the one question that best repairs it. The original Phase 5C description in docs/MASTER_PLAN.md bundled this together with "adaptive selection" (a global, mastery-driven next-question queue); this phase brief explicitly split them — **5C-2 is targeted repair selection, 5C-3 (not started) is global adaptive selection** — and this decision documents why they must not be merged.
**Decision:**
- **Why deterministic, not AI-chosen:** the phase brief was explicit that the actual question choice must be deterministic and explainable from observable evidence and Question DNA, never an opaque model call. `@ipmat/repair-selection` (new package, `packages/domain/repair-selection`) has no dependency on `@ipmat/ai` in its own source — `selectRepairQuestion()` is a pure function over a `RepairPlan` and a list of candidate questions, with no AI call anywhere in the selection path itself (only the UPSTREAM hypothesis that produced the `RepairPlan` ever called an AI provider, and that's `@ipmat/autopsy`'s job, not this package's).
- **Eligibility, before ranking:** three gates apply, in order, to the WHOLE candidate pool before any tier comparison happens: (1) structural Question DNA completeness (`validateRepairCandidateQuestion()` — a malformed candidate is excluded and counted, never silently scored); (2) `validationState === "published"` AND `conceptName` matches the plan's target concept (a repair question is always about the diagnosed concept; never a "generic practice" substitution from an unrelated concept); (3) the `recommendedTrainingMode`'s hard DNA requirement, applied UNIFORMLY across every tier — `timed_pressure_drill` requires `testingModes` to include `"time_pressured"`, `novelty_exposure` requires a non-`"standard"` `noveltyLevel`. This third gate is never relaxed for a broader "fallback" — if nothing satisfies the prescribed training mode, that is reported as `"no_match"` (`training_mode_constraint_unsatisfied"`), not silently downgraded to a question that doesn't actually address the training-mode-specific weakness.
- **How eligibility narrows to ONE question — explicit tiers, not a score:** `classifyMatchTier()` (`matchTier.ts`) assigns every eligible candidate to exactly one of 6 named, ordered tiers (`direct_cell_and_trap` > `direct_cell` > `pattern_family_and_trap` > `trap_only` > `pattern_family` > `concept_fallback`) — see the doc comment on `REPAIR_MATCH_TIER_ORDER` for the full definition of each. Ranking `trap_only` (same confirmed error category, different pattern family) ABOVE a bare `pattern_family` match is a deliberate, documented judgment call — directly repairing the diagnosed error is treated as more relevant than merely repairing the same question structure without addressing why the student got it wrong — not an arbitrary weight; no composite numeric score exists anywhere in this package.
- **Tie-breaking:** within the single winning tier, `tieBreak.ts` applies a FIXED, documented order: (1) overuse avoidance (`applyOveruseAvoidance()` — a candidate attempted at/above `REPAIR_SELECTION_CONSTANTS.OVERUSE_MIN_ATTEMPT_COUNT`, provisional like every other centralized threshold in this codebase, is excluded ONLY when a fresher alternative exists in the same tier — never allowed to empty it); (2) a detected speed weakness (reusing `@ipmat/autopsy`'s OWN `AUTOPSY_THRESHOLDS.SLOW_SPEED_RATIO` via `detectSpeedProblem()`, never a second invented threshold) prefers the candidate with the shorter `expectedTimeSeconds`; (3) difficulty-tier proximity to the originally diagnosed question's tier, using a small, explicit, documented rank array (`DIFFICULTY_RANK`), not a claim that difficulty is generally linear (consistent with D-021's existing "provisional" caveat); (4) lexicographically smallest `questionId` as the final, always-decisive tie-break, making every selection reproducible.
- **What happens when direct repair is unavailable:** `concept_fallback` is the one tier that is EXPLICITLY a deliberate fallback — `RepairSelectionResult.isFallback` is `true` only for it, and its generated `explanation` always reads "Direct repair unavailable for ... ; broader concept-level repair selected as a deliberate fallback," matching the phase brief's required phrasing exactly. A caller can always distinguish "we found the best available match" from "we had to fall back to the concept level" without parsing free text.
- **Why corrected free-text is never automatically classified:** `selectRepairQuestion()`'s only diagnosis-side input is a `RepairPlan`, and `buildRepairPlan()` (`@ipmat/autopsy`, D-039) is the ONLY function that constructs one — it already refuses for every `confirmationStatus` except `"confirmed"`, so an awaiting/rejected/corrected hypothesis never produces a `RepairPlan` at all, and therefore never reaches this package. `selectRepairQuestion()` ALSO re-verifies `repairPlan.confirmationSource?.hypothesisConfirmedAt` itself before doing anything else (`RepairSelectionError("not_confirmed", ...)` otherwise) — the same defense-in-depth "never trust a value merely typed as X" discipline `@ipmat/db`'s repository validation layer already established (D-043), guarding against a `RepairPlan`-shaped object constructed some other way. A `"corrected"` hypothesis's `studentCorrectionText` is preserved verbatim by `@ipmat/autopsy` itself (unchanged in this phase) and never reaches a structured taxonomy category anywhere in this package, because it never produces a `RepairPlan` to select from in the first place.
- **What is intentionally NOT adaptive yet (5C-3 boundary):** this package has no concept of "what should this student practice next in general," no cross-concept prioritization, no mastery-driven queue, and does not read `MasteryState` at all. It answers exactly one question: "given THIS ONE confirmed diagnosis, which of the available questions repairs it." Global, mastery-aware "what's the single best use of this student's next 10 minutes" logic is Phase 5C-3's job, deliberately not started here — merging the two would make it impossible to test or reason about either in isolation, which is exactly the boundary the phase brief asked to preserve.
**Consequences:** `RepairCandidateQuestion` composes `@ipmat/autopsy`'s existing `AutopsyQuestionContext` with `expectedTimeSeconds`/`validationState` (the two fields that type deliberately omits) rather than inventing a third parallel Question DNA shape — see `packages/domain/repair-selection/src/types.ts`. No new Prisma/schema changes were needed for this phase; `@ipmat/repair-selection` is, like every other domain package, database-independent (depends on `@ipmat/autopsy`/`@ipmat/examiner-lens`/`@ipmat/question-engine`/`@ipmat/ai`/`@ipmat/attempt`, never `@ipmat/db`) — proven by the same architecture-boundary test pattern D-043 introduced.

## D-046 — `AttemptRepository` (Phase 4B-1) is the first repository with a genuine multi-write sequence, requiring an actual `$transaction`, and re-enforces ownership/finalization invariants the domain layer alone cannot check against persisted history

**Status:** Accepted
**Context:** Phase 5C-1 built the first repository/adapter layer in this codebase (`Autopsy`/`RepairPlan`/`MasteryState`) and explicitly documented that none of those needed a transaction, because each performs exactly one write. `@ipmat/attempt`'s `AttemptState` is different: it owns a variable-length child collection (`AttemptEvent[]`) alongside its own parent row, and Phase 4B-1 was asked to persist and retrieve both faithfully.
**Decision:**
- **A genuine multi-write sequence, wrapped in `$transaction`:** `PrismaAttemptRepository.save()` upserts the `attempts` row, deletes its existing `attempt_events` rows, and recreates them from `state.events` — a real 3-part write (parent + child-delete + child-recreate), the first case in this codebase where Phase 5C-1's "no transaction needed, only one write" reasoning does NOT apply. Left unwrapped, a crash between the delete and the recreate could leave a real attempt with zero persisted events despite a genuine event history — exactly the "partially written logical object" a transaction exists to prevent. `save()` uses Prisma's array-form `$transaction([...])` (independent statements executed atomically), not an interactive transaction, since none of the writes need to branch on another write's result.
- **Full replace, never an incremental diff:** rather than tracking "which events were already persisted" and inserting only new ones, every `save()` call deletes and fully rewrites the event collection from `state.events`. This is deliberately the simpler of the two designs Phase 4B-1 considered — no precedent for incremental sync exists anywhere in this codebase, and for a quiz question's handful of events, rewriting all of them on every save has no meaningful cost. This also directly guarantees "persisted data reconstructs the domain `AttemptState` faithfully" (the phase's own requirement): what's in the database IS exactly `state.events`, never a delta that could drift from it.
- **Events always persist in `@ipmat/attempt`'s own canonical order, never the caller's raw array order:** `save()` calls the domain package's own exported `getEventTimeline()` before writing, reusing existing domain logic rather than re-implementing "what order did this actually happen in" a second time (the phase brief's explicit "reuse the existing domain finalization logic; do not duplicate business rules" instruction). Proven directly: a test hand-constructs a deliberately out-of-order `events` array (something the real lifecycle functions could never produce, since they reject any non-monotonic timestamp on append) and confirms it still round-trips in canonical order.
- **Ownership/linkage enforced a second time, at a boundary the domain layer cannot reach:** `@ipmat/attempt`'s own `assertOwnership()` checks an in-memory `AttemptState` against a caller-supplied claim — it has no way to compare against a SEPARATELY STORED prior version of the row, because in a pure domain package there is no such thing. `assertAttemptOwnershipUnchanged()` (`packages/db/src/repositories/validation.ts`) is the persistence boundary's OWN invariant: an attempt's `studentId`/`questionId`/`enrollmentId` can never change across two saves of the same id, once a row already exists.
- **Finalization invariants enforced a second time, for the same reason:** "no code path re-opens a finalized attempt" (D-035) is a domain-layer guarantee for anything produced by `@ipmat/attempt`'s own lifecycle functions operating on one in-memory object — it says nothing about whether an EARLIER, separate `save()` call already finalized this id. `assertAttemptNotRegressingFromFinalized()` refuses to persist a status change away from an already-terminal persisted status (an idempotent resave of the SAME terminal status is allowed, since that's not a regression). `assertAttemptStateInternallyConsistent()` additionally re-checks the same status/chosenAnswer/isCorrect/finalizedAt/timeSpentSeconds nullability rules `applyFinalization()` already guarantees for anything it produces — defense against an `AttemptState`-shaped value that merely has the right TypeScript shape without ever having gone through a real lifecycle function, the same "never trust a value merely typed as X" discipline D-043/D-044 already established.
- **Foreign-key existence checked only for a brand-new attempt, not every save:** `Student`/`Question`/`Enrollment` (and `retryOfAttemptId`, if set) are verified to exist via real Prisma queries the first time an id is saved — once a row exists, ownership-unchanged checking already guarantees those three ids can't silently become something else, so re-verifying their existence on every subsequent save (of the same, already-validated ids) would be redundant work with no safety benefit.
- **No id generation inside the repository:** `AttemptState.id` is always caller-supplied (from `startAttempt({id, ...})`, per the domain package's own pure-function convention) and written verbatim — the repository never lets Prisma's `@default(uuid())` generate a DIFFERENT id than the one the in-memory domain object already claims, which would silently break "persisted data reconstructs the domain AttemptState faithfully."
- **No schema/migration change:** the existing `attempts`/`attempt_events` tables and their `AttemptStatus`/`AttemptEventType` enums (Phase 1) already match the domain package's vocabulary exactly — confirmed field-by-field before writing any repository code, not assumed.
**Consequences:** `InMemoryAttemptRepository` (`packages/db/test/fixtures/inMemoryRepositories.ts`) calls the EXACT SAME `assertAttemptStateInternallyConsistent()`/`assertAttemptOwnershipUnchanged()`/`assertAttemptNotRegressingFromFinalized()` functions `PrismaAttemptRepository` calls, and also calls `getEventTimeline()` before storing — the two implementations cannot silently diverge on what counts as valid or in what order events end up stored, the same discipline D-043 established for the Phase 5C-1 repositories. Its foreign-key checking is opt-in (`knownStudentIds`/`knownQuestionIds`/`knownEnrollmentIds`, each independently omittable) rather than always-on, since most round-trip tests don't care about FK validation and forcing every test to supply three sets would add friction with no corresponding safety benefit in a test double.

**Addendum (Phase 4B-1 final review, same phase, before first commit) — three findings, all fixed within the persistence layer, none requiring a schema change or a change to `@ipmat/attempt`:**
1. **TOCTOU on the preflight existence read.** The original `save()` read `existing` via a plain `findUnique()` OUTSIDE the write transaction, then made its ownership/finalization decisions from that snapshot before writing. Two genuinely concurrent `save()` calls for the same attempt id could both read the same pre-write snapshot, both pass their invariant checks against it, and then both commit — a silent lost update, not a crash, so the array-form `$transaction`'s atomicity guarantee did nothing to prevent it (atomicity guarantees each transaction's OWN writes are all-or-nothing; it says nothing about two transactions racing each other). Fixed by moving the ENTIRE read-check-write sequence into one Prisma interactive transaction (`$transaction(async (tx) => {...})`) at `Serializable` isolation — Postgres itself now detects a genuine conflict between two such transactions and aborts the losing one with a serialization-failure error, rather than silently applying a lost update. This is a real correctness property by construction (documented Postgres/Prisma transaction semantics), not empirically verified, since no live database has ever been reachable in this environment to actually provoke the race.
2. **`retryOfAttemptId` was excluded from `assertAttemptOwnershipUnchanged()` and from the `upsert`'s `update` data.** A resave with a DIFFERENT `retryOfAttemptId` than the one the row was created with would have that discrepancy silently discarded (the DB value simply never changes) rather than rejected — inconsistent with how the other three identity fields were already protected. Fixed by adding `retryOfAttemptId` to `assertAttemptOwnershipUnchanged()`'s comparison; `update` still deliberately omits it (now provably safe to omit, since a change would already have been rejected before reaching the upsert).
3. **Event read-back ordering had no deterministic tie-break for events sharing the exact same `occurredAt`.** `@ipmat/attempt`'s own `assertTimestampIsCoherent()` permits equal-but-never-decreasing timestamps, and `getEventTimeline()`'s own stable sort resolves such ties by preserving array (append) order — but `findById()`'s `ORDER BY occurred_at ASC` alone has no guaranteed tie-break matching that original append order. Fixed by writing each `AttemptEvent.id` explicitly as `${attemptId}:${zero-padded index}` (instead of Prisma's random `@default(uuid())`) at write time, matching `getEventTimeline()`'s already-decided order, and adding `id: "asc"` as a secondary `orderBy` key at read time — a fully deterministic, write-order-preserving tie-break requiring no schema change, rather than relying on unspecified database behavior for ties. `getEventTimeline()` remains the ONE place canonical event order is DECIDED; this only makes the read path faithfully reproduce whatever it decided, including for ties.

3 new tests added for findings 2 and the self-retry case (which was already correctly rejected as a side effect of the FK-existence check running before the row is written — documented with a test rather than left as an untested implicit behavior). Finding 3 has no dedicated test: it is Prisma/Postgres-specific behavior that cannot be exercised against `InMemoryAttemptRepository` (which has no SQL tie-break problem to begin with) and, like everything else Prisma-related in this codebase, has never run against a live database.

## D-047 — Practice-loop orchestration (Phase 4B-2) is a new TOP-LEVEL package, not a domain package; `InMemoryAttemptRepository` is promoted to `@ipmat/db`'s production surface, the same `FixtureProvider` precedent

**Status:** Accepted
**Context:** Phase 4B-2 needed an application-facing layer that wires `@ipmat/attempt`'s pure lifecycle functions to a persisted `AttemptRepository` (Phase 4B-1) — genuinely new code, but not obviously domain logic, not a UI, and not infrastructure either. Two placement questions needed resolving before writing any code: where does orchestration code that depends on a persistence PORT (not a concrete Prisma class) belong, and how should its tests get access to `InMemoryAttemptRepository` without either duplicating it or reaching across a package boundary into another package's `test/` directory.
**Decision:**
- **New package, `packages/practice-loop` (`@ipmat/practice-loop`), sits OUTSIDE `packages/domain/*`.** `@ipmat/attempt` (pure, database-free) is a domain package; `PracticeLoopService` is not — it depends on `AttemptRepository`, an interface defined in `@ipmat/db`, and domain packages must never depend on `@ipmat/db` (docs/ARCHITECTURE.md §6). Placing it under `packages/domain/*` would either violate that boundary or require inventing a fake abstraction just to satisfy the folder convention. Instead it sits at the top level, sibling to `ai`/`db`/`jobs` — the SAME precedent docs/ARCHITECTURE.md §4 already names for `/jobs` ("not built, Phase 3... BullMQ job definitions + workers"): an orchestration layer that wires domain logic and infrastructure together belongs one level above pure domain, not inside it.
- **Zero business-logic duplication:** every `PracticeLoopService` method that mutates an attempt follows the identical `load -> pass directly into the real @ipmat/attempt function -> persist whatever it returns` shape. No lifecycle rule, error code, or correctness/timing computation is re-implemented — `submitAttempt()`'s signature has no parameter through which a caller could supply `isCorrect`/`chosenAnswer`/`timeSpentSeconds` directly, the identical structural guarantee D-034 already established one layer down, now also true one layer up. Errors from `@ipmat/attempt` (`AttemptLifecycleError`) and `@ipmat/db` (`PersistenceError`) are never caught or re-wrapped — they propagate to the caller exactly as thrown.
- **The one genuinely new rule this layer owns:** `PracticeLoopError("question_not_published")` refuses to start an attempt against a question whose `validationState !== "published"`. This is NOT a duplicate of anything `@ipmat/attempt` checks (it has no concept of publication state at all) — it is this layer's own, narrowly-scoped business rule, extending "no fake AI, no fake analytics" to "no fake practice content." Given Phase 3.5 currently has zero published questions, this gate correctly refuses to run against every one of Phase 3.5's 7 new candidates today — proven by tests, not just asserted.
- **`InMemoryAttemptRepository` moved from `packages/db/test/fixtures/inMemoryRepositories.ts` into `packages/db/src/repositories/inMemoryAttemptRepository.ts`, and is now exported from `@ipmat/db`'s production `src/index.ts`.** This mirrors an ALREADY-EXISTING precedent in this exact codebase: `FixtureProvider` (`packages/ai/src/providers/fixtureProvider.ts`) is a deterministic test double that has always lived in `@ipmat/ai`'s production `src/`, specifically so every OTHER package's tests can depend on it via the package name. Before this move, `@ipmat/practice-loop`'s tests would have needed either a raw relative import reaching across a package boundary into `@ipmat/db`'s `test/` directory (a real risk: TypeScript's `rootDir` constraint can reject files outside a project's own root during a real `tsc` build, not just at typecheck) or a second, hand-duplicated in-memory `AttemptRepository` implementation — the phase brief explicitly forbade the latter ("Do not add a second persistence implementation"). `packages/db/test/fixtures/inMemoryRepositories.ts` now re-exports it from the new location, so `@ipmat/db`'s own existing tests (`attemptRepository.test.ts`) needed no changes at all. `InMemoryAutopsyRepository`/`InMemoryRepairPlanRepository`/`InMemoryMasteryStateRepository` were deliberately NOT moved — nothing outside `@ipmat/db`'s own tests currently needs them, and moving them would be unrequested, unrelated surgery on Phase 5C-1's existing structure.
**Consequences:** `@ipmat/practice-loop` depends on `@ipmat/attempt` and `@ipmat/db` — never `@prisma/client` directly; its constructor takes the `AttemptRepository` INTERFACE, so a future caller can inject `PrismaAttemptRepository` (production) or `InMemoryAttemptRepository` (tests) interchangeably. This phase builds ONLY the orchestration layer itself — no HTTP route, no UI, and no change to Phase 4B's own exit criterion, which remains unmet pending Phase 3.5 producing a real published question and a live database becoming reachable. **Superseded in part by D-048:** the original revision of this phase accepted a caller-supplied `PracticeQuestion` (including `correctAnswer`/`validationState`) as a parameter to `startAttempt()`/`submitAttempt()`, which a security review found to be a genuine authority gap; the constructor now also takes an injected `QuestionReader`, and `@ipmat/practice-loop` no longer depends on `@ipmat/question-engine` at all (it never names `ValidationState` directly — only `@ipmat/db`'s `CanonicalQuestion`/`QuestionReader` types do).

## D-048 — Practice-loop's client-facing input must never carry a Question's answer key or publication state; a QuestionReader PORT resolves both server-side

**Status:** Accepted
**Context:** A read-only security/correctness review of Phase 4B-2 (before it was committed) asked the exact right question: is the `PracticeQuestion` object `PracticeLoopService.startAttempt()`/`submitAttempt()` accepted as a parameter actually authoritative, or could an eventual untrusted HTTP/UI caller supply or manipulate it? The answer was a genuine, severe gap. `PracticeQuestion extends AttemptQuestionContext`, so the ORIGINAL signature required the caller to hand the service `correctAnswer`, `options`, `expectedTimeSeconds`, AND `validationState` on every call — every one of D-034's grading guarantees ("chosenAnswer/isCorrect are always derived, never accepted as client input") was reintroduced one layer up, since `@ipmat/attempt`'s own `submitAttempt(attempt, claim, question, {now})` only ever checks `question.questionId === attempt.questionId` (an identity match) — it has no way to know whether `question.correctAnswer` is the REAL answer for that id, because that was never its job; the CALLER was supposed to be trusted for that, and once the caller is an HTTP/UI client, it cannot be. Concretely, against the pre-fix code: (1) a client could submit any `correctAnswer` it liked and always be graded correct; (2) a client could label any question `validationState: "published"` regardless of its real state, defeating the ONE gate this layer existed to enforce; (3) `expectedTimeSeconds`/`options`/`conceptId` were equally forgeable; (4) `submitAttempt()`'s own `questionId` check only compares the ID STRING, so a client could supply a real `questionId` alongside a completely fabricated rest-of-the-question payload; (5) since `correctAnswer` was a REQUIRED field on the client-facing input type, any real browser client would necessarily need to know or reconstruct the answer key just to call the API at all — structurally defeating the purpose of server-side grading.
**Decision:**
- **New `QuestionReader` port + `CanonicalQuestion` type, defined in `@ipmat/db`'s `repositories/types.ts`** (same file/convention as `AttemptRepository`, since `PracticeLoopService`'s consumer-side dependency on an `@ipmat/db`-defined persistence port was already the established pattern). `CanonicalQuestion` restates only the subset of the real `Question` Prisma model this layer needs (`id`, `conceptId`, `options`, `correctAnswer`, `expectedTimeSeconds`, `validationState`) — never constructed from client input, only ever returned by a `QuestionReader` implementation.
- **`PrismaQuestionReader` (production, `packages/db/src/repositories/prismaQuestionReader.ts`)** is a genuinely READ-ONLY adapter over the existing `Question` table — it never writes a row, matching this phase's explicit non-goal of question generation/publication. `answerFormat` is derived (`options !== null` → `multiple_choice`) rather than requiring a new schema column, since the real `Question.options` (`Json`, non-nullable) is the only existing signal for it.
- **`InMemoryQuestionReader` (test double, `packages/db/src/repositories/inMemoryQuestionReader.ts`)**, promoted straight into `@ipmat/db`'s production `src/`, the identical `FixtureProvider`/`InMemoryAttemptRepository` precedent (D-047) — so `@ipmat/practice-loop`'s tests depend on it via the package name, never a cross-package `test/` import.
- **`PracticeLoopService`'s constructor now takes BOTH `AttemptRepository` AND `QuestionReader`.** `startAttempt()`'s client-facing input shrank to an identifier — `questionId: string` — never a question-content object; the service loads the canonical question itself and independently checks `validationState === "published"` before starting anything. `submitAttempt()`'s client-facing input shrank to `{attemptId, claim, now}` — NO question parameter at all; the question graded against is resolved via `existing.questionId`, the value ALREADY persisted on the attempt row the caller is submitting against, which closes the cross-substitution gap (threat 4) as a structural consequence, not a new check. `PracticeQuestion` (the vulnerable type) was deleted from `@ipmat/practice-loop`'s public surface entirely; `@ipmat/attempt`'s own `submitAttempt()` signature was NOT changed — the fix is entirely in what `PracticeLoopService` is willing to accept from its caller and where it gets `AttemptQuestionContext` from.
- **New `PracticeLoopError("question_not_found")`** alongside the existing `"question_not_published"`, for when a supplied `questionId` doesn't resolve to any canonical question at all (a case the old signature couldn't distinguish, since the caller always supplied SOME question payload).
**Consequences:** `@ipmat/practice-loop` now depends on `AttemptRepository` AND `QuestionReader`, both from `@ipmat/db`, for every method that touches question content; a future HTTP/API layer can only ever pass identifiers and observable student actions, never an answer key. `InMemoryAttemptRepository`/`InMemoryQuestionReader`'s placement in `@ipmat/db`'s production `src/` was reviewed again as part of this fix (the review explicitly asked whether it was 'architecturally justified or merely convenient') and left unchanged — it is the same real precedent as `FixtureProvider`, and no new issue with it was found. 6 new tests cover the previously-nonexistent authority boundary (cross-question correctAnswer substitution, submit-time question-identity substitution, canonical options enforcement, question_not_found on both start and submit) alongside the 20 existing tests, updated to the new call signatures — 26 tests total in this package, 467 across the repo, typecheck/lint/build all clean. Still NOT done: this package still has no caller (no HTTP/UI layer exists yet), so this fix has not been exercised end-to-end against a real request; that remains true of the whole practice-loop foundation until Phase 4B's own exit criterion is met.

## D-049 — Explicit human question publication is a new `decidePublication()` domain function over the REAL persisted `ValidationState`, applied through a narrow `QuestionPublicationRepository` that only ever takes an action, never a raw target state

**Status:** Accepted
**Context:** Phase 3.5's own status has read "human publication review: PENDING" since the fixture-driven coverage-expansion pass — nothing in this codebase has ever been ABLE to publish a Question, only able to leave one at `validated`/`review_required` in the generation pipeline's own in-memory result. The next unit of work asked for the smallest clean foundation letting an authorized human/process inspect an already-persisted Question and explicitly decide `publish` or `reject`, with "validated" never implying "published," a required prerequisite check, and no code path that could accidentally promote a `rejected` row. A read-only inspection first surfaced an important existing fact: this codebase has TWO overlapping but distinct status vocabularies — `QuestionLifecycleStatus` (`lifecycle.ts`: `draft/generated/validated/review_required/approved/published/rejected/deprecated`), the generation PIPELINE's own in-memory candidate status, produced by `computeLifecycleStatus()` and never persisted anywhere; and `ValidationState` (`draft/ai_validated/human_reviewed/published/rejected`), the REAL enum on the Prisma `Question.validationState` column, which is what `@ipmat/practice-loop`'s `QuestionReader` gate and everything else that has ever touched a real Question row actually reads. The inspection also found: none of Phase 3.5's 7 candidates has EVER been persisted as a real `Question` row (no candidate→`Question` writer exists anywhere), no `QuestionRepository` of any kind existed before this pass, the schema already has a hand-written DB-level CHECK constraint `questions_published_requires_provenance` (migration `0001_init`) enforcing "published requires provenance" independently of anything application-level, and the `Question`/`Provenance` models have no actor/reviewer/audit column anywhere.
**Decision:**
- **`decidePublication(action, input)` operates on `ValidationState`, NOT `QuestionLifecycleStatus`.** Requirement 12 ("do not invent a new question model if the existing Prisma lifecycle already supports the needed state") is satisfied literally: `ValidationState` is that existing Prisma lifecycle. `QuestionLifecycleStatus`/`computeLifecycleStatus()`/`lifecycle.ts` are completely untouched — the generation pipeline is not rewritten, per the phase brief. The task's own test framing ("a `review_required` candidate cannot be published...") maps onto this design as: a Hard/Extreme/Novel-tier row sitting at `ai_validated` (the pipeline's `review_required` territory, pre-persistence) is blocked from publishing until it reaches `human_reviewed` — the SAME prerequisite, expressed in the persisted vocabulary rather than a second, parallel one.
- **`decidePublication()` is pure and database-free** (`packages/domain/question-engine/src/publicationDecision.ts`) and throws a typed `PublicationDecisionError` (mirroring `@ipmat/attempt`'s `AttemptLifecycleError` style — a definite result or an exception, never a silently-ignorable `{ok: false}`) for: `currentValidationState` already terminal (`published`/`rejected` — neither can be the CURRENT state of an incoming decision, extending D-006/D-035's "no reversing a terminal state" to content); validation not yet complete (anything before `ai_validated`); a tier requiring human review (`requiresHumanReview()`, reused verbatim from `lifecycle.ts`, not restated) that hasn't reached `human_reviewed`; or no Provenance attached. Nothing in the generation pipeline calls this function — reaching `ai_validated` never implies `published` on its own (requirement 3/4), and this remains true regardless of how many other phases are built on top, since only an explicit, separate call can invoke it.
- **`QuestionPublicationRepository` (port, `@ipmat/db`) + `PrismaQuestionPublicationRepository` (production) + `InMemoryQuestionPublicationRepository` (test double, same `FixtureProvider`/`InMemoryAttemptRepository`/`InMemoryQuestionReader` precedent) is the ONLY write path to `Question.validationState` anywhere in this codebase.** Its `decide(questionId, action)` takes an ACTION (`"publish" | "reject"`), never a raw target `ValidationState` — there is no method on this interface, in either implementation, that would let a caller construct a pre-approved target state and skip `decidePublication()`; both implementations independently load the row's CURRENT state themselves (never trusting a caller's claim about it, the same D-048 lesson one layer over) and run it through the SAME shared `decidePublication()` before writing. This satisfies requirement 5 (rejected content can never become publishable through an "ordinary" save/update) by construction: there IS no ordinary save/update — this narrow repository is not a general Question CRUD surface (no `body`/`options`/`correctAnswer`/etc. in its read/write shape), so requirement 6's "fail closed" and requirement 1's "preserve provenance/validation state" hold structurally, not by convention. `PrismaQuestionPublicationRepository.decide()` wraps the load-decide-write sequence in one `$transaction`, the same atomicity pattern `PrismaAttemptRepository` established (Phase 4B-1).
- **No actor/audit record was added.** The schema has no reviewer/actor column on `Question` or `Provenance`, and the phase brief's own "Prefer" list said not to introduce one unless the existing schema had a clean place for it — it doesn't, so none was added (requirement 11's "keep the boundary explicit and injectable IF an actor identity is required BY THE SCHEMA" — it currently is not). This is an explicitly acknowledged, deferred gap, not an oversight: a real curation workflow will eventually need to know WHO decided, and that is future schema work, not a quiet omission here.
- **Fixture-vs-real-model distinguishability (requirement 2) required no new mechanism.** `AiResultMetadata.model`/`.provider` (`@ipmat/ai`, already existing) already distinguish `"fixture-deterministic-v1"` from a real Anthropic model name on every `GenerationPipelineResult`; this workflow operates on an already-persisted Question row's `validationState`/`difficultyTier`/provenance, fields that exist independently of how the row was produced, and never discards or merges that metadata with anything.
**Consequences:** `@ipmat/question-engine` gains one new pure, tested module; `@ipmat/db` gains one new narrow read/write port with Prisma and in-memory implementations. 31 new tests (13 pure-function in `@ipmat/question-engine`, 18 repository-level in `@ipmat/db`, covering: the repository contract, consistency with `@ipmat/practice-loop`'s `QuestionReader`-based publication gate, the concurrency fix below, and structural regression guards against the isolation-level fix being silently removed later) — 498 across the repo, typecheck/lint/build all clean. **None of Phase 3.5's 7 candidates was published, or even touched, by this work** — they have never been persisted as `Question` rows, so this is infrastructure with nothing yet to apply it to; the published-question count remains 0, and Phase 3.5's human-publication-review status remains PENDING, now for lack of an actual decision rather than for lack of a way to make one. Still NOT done: a candidate→`Question` writer (so a Phase 3.5 candidate could become a real row this workflow could act on), any actual publish/reject decision against real content, and an actor/audit trail (deferred pending a schema decision).

**Addendum (same decision, follow-up correctness review): `decide()` needed `Serializable` isolation, the same fix D-046 already applied to `PrismaAttemptRepository`, for the identical reason.** The original implementation wrapped `findUnique` + `decidePublication()` + `update()` in a plain `$transaction` with NO explicit isolation level, which defaults to Postgres's READ COMMITTED — under which a bare `findUnique` takes no row lock, so two concurrent `decide()` calls for the same question (e.g. one `"publish"`, one `"reject"`) could both read the same non-terminal `validationState`, both independently pass `decidePublication()` against that shared snapshot, and both issue a blind `update({ where: { id } })` — whichever committed second would silently overwrite the first's already-committed terminal decision, since a plain `update()`'s `WHERE` clause matches on `id` alone, never on the `validationState` it was actually read against. This is a genuine lost-update / terminal-state-reversal bug, unrelated to caller authorization (authorization and transactional correctness are orthogonal). Considered and rejected: an optimistic conditional `updateMany({ where: { id, validationState: <value read> } })` + affected-row-count check — technically also correct (and it would work at plain READ COMMITTED), but it is a SECOND, different concurrency-control technique from the one already established and reviewed for `PrismaAttemptRepository`, and this is a simpler case (a single-row, single-column state check) that Postgres's `Serializable` Snapshot Isolation already handles as its canonical "write skew" scenario — matching existing precedent (D-046) was judged the smaller, more consistent fix, not a new pattern to maintain. Fixed by adding `{ isolationLevel: Prisma.TransactionIsolationLevel.Serializable }` to `decide()`'s `$transaction` call — one line, no interface change, no change to `@ipmat/question-engine`. The existing DB-level CHECK constraint (`questions_published_requires_provenance`) is a separate, narrower invariant (provenance presence, evaluated against the row's actual state at commit time) that does not by itself protect against the terminal-state race, and remains in place as defense-in-depth for its own, different rule — not a substitute for the isolation-level fix. 6 more tests added: 5 code-level tests against a hand-rolled fake `PrismaClient` (proving `decide()` actually requests `Serializable` isolation, and that a refused decision never reaches `update()` at all — deterministic, provable without a live database) and 1 in-memory concurrent-call test whose own doc comment explicitly states what it does NOT prove (it is safe only because `InMemoryQuestionPublicationRepository.decide()` has no internal `await`, a property of Node's execution model with no bearing on real concurrent Postgres connections). **Whether Postgres's `Serializable` isolation actually aborts the conflicting transaction the way this fix's own doc comment describes remains unverified against a live database — the same standing caveat as every other `PrismaXRepository` in this codebase (D-046).**

## D-050 — Candidate -> persisted Question import is a narrow `QuestionImportRepository` write path, gated by a pure `assertCandidateIsImportable()` that only ever accepts pipeline status `"validated"`

**Status:** Accepted
**Context:** Phase 3.5 has 7 fixture-driven candidates (`percentagesCoverageExpansion.ts`) that reach either `"validated"` (2, advanced/standard tier) or `"review_required"` (5, hard/extreme tier) — but NONE has ever been persisted as a real `Question` row, and no candidate→`Question` writer existed anywhere in this codebase before this pass (confirmed by a read-only inspection: zero `prisma.question.create` calls outside `prisma/seed.ts`'s own hand-authored demonstration question). The publication workflow (D-049) therefore had, until now, nothing real to act on. A read-only inspection also surfaced the exact shape of the gap to close: `QuestionCandidateAiOutput` (the AI-generation schema, `@ipmat/ai`) carries content and Question DNA but no exam/section/chapter identity (that lives on the ECHOED `QuestionBlueprint`, `GenerationPipelineResult.blueprint`); the real `Question` Prisma model has SEVEN foreign keys (`examId`, `sectionId`, `chapterId`, `conceptId`, `patternTaxonomyCellId`, `trapErrorTaxonomyId`, `provenanceId`) that must all be resolved by NATURAL KEY, since a candidate only ever carries names/codes, never database ids; and `PatternTaxonomyCell` already has a real compound `@@unique([conceptId, patternFamilyId, testingMode, trapErrorTaxonomyId, difficultyTier])` — the cell is a pre-existing Question-Universe mapping (Phase 2's Examiner Lens step), never something an import should create.
**Decision:**
- **`assertCandidateIsImportable()` (pure, database-free, `packages/domain/question-engine/src/candidateImport.ts`) is the ONE gate, and it accepts only pipeline status `"validated"`.** `"review_required"` and `"rejected"` are BOTH refused, fail closed, with `CandidateImportError`. This is deliberate, not merely conservative: `computeLifecycleStatus()` (unchanged) already guarantees Hard/Extreme/Novel tiers can never reach `"validated"` — they always land in `"review_required"` (`requiresHumanReview()`, D-008) — so refusing `"review_required"` costs nothing today, and the existing 5-value `ValidationState` enum has no state that would legitimately represent "persisted but still needs human review" anyway. A Hard/Extreme/Novel candidate therefore has NO import path yet, by design — inventing one (e.g. a new `ValidationState` value) was explicitly out of scope ("do not invent a new question model if the existing Prisma lifecycle already supports the needed state"). The gate reuses the pipeline's OWN verdict rather than re-running `validateCandidateStructurally()`/`verifyComputation()`/etc. a second time — those already ran inside `runGenerationPipeline()`; re-running them here would be exactly the "duplicate validation logic" this function exists to avoid.
- **Persisted `validationState` is always `"ai_validated"`, matching the SAME "validated -> ai_validated" mapping `coverageExpansion.test.ts` already established** for a different purpose (coverage counting) — reused here, not reinvented. Never `"published"` — the only later path to `"published"` remains `QuestionPublicationRepository.decide(id, "publish")` (D-049); nothing in the importer calls it.
- **`QuestionImportRepository` (port, `@ipmat/db`) + `PrismaQuestionImportRepository` (production) + `InMemoryQuestionImportRepository` (test double, seeded with a plain "reference world" of exams/sections/chapters/concepts/pattern families/error taxonomies/taxonomy cells) is the ONLY write path from a validated candidate to a `Question` row.** `importValidatedCandidate()` accepts exactly `{ blueprint, candidate, status, provenance }` — the SAME shape a real `GenerationPipelineResult` carries, plus provenance metadata — never a hand-assembled DTO with independently-settable `correctAnswer`/`difficultyTier`/`validationState`/an existing `provenanceId`. The implementation calls `assertCandidateIsImportable()` itself before touching anything, so a caller cannot bypass the gate by skipping a pre-check (the same defense-in-depth discipline as D-048/D-049).
- **FK resolution is entirely natural-key-based, via `findUnique`/`findFirst` against the EXISTING schema, and NEVER creates a `PatternTaxonomyCell`** (or any other reference row) — a missing cell/concept/family/trap/exam/section/chapter fails closed with `PersistenceError("missing_reference")`. `PatternTaxonomyCell`'s lookup uses `findFirst`, not `findUnique` on its compound-unique input, because Prisma's generated compound-key type for that constraint cannot express matching a `NULL` `testingMode`/`trapErrorTaxonomyId` — `findFirst` is safe here specifically BECAUSE the real `@@unique` guarantees at most one match.
- **Idempotency key: `(patternTaxonomyCellId, body)`** — the strongest EXISTING identifiers available (a real resolved FK plus the exact stem text), chosen over the fuzzy `checkDuplicateRisk()` heuristic (that solves a different problem — near-duplicate CONTENT across the whole bank — not exact re-import detection) and over a schema migration (no new column was added; "do not invent a weak text-based deduplication rule if a stronger existing identity exists" was read as "ground the choice in what identifiers already exist," not "add a new one"). A repeat import of the same candidate returns the existing row (`alreadyExisted: true`); a genuinely different candidate against the same cell imports as a distinct row.
- **Provenance is always a FRESH `Provenance` row, created from caller-supplied `{sourceType, sourceRef?, licenseRef?, attributedTo?}`, never an existing `provenanceId`** — using the existing schema's own fields, never a parallel provenance system.
- **`Serializable` isolation** (matching D-046/D-049's now-established discipline) wraps the whole read-resolve-write sequence in `PrismaQuestionImportRepository`, for the same read-then-blind-write reasons already documented there.
- **Explicitly out of scope:** updating `PatternTaxonomyCell.coverageStatus` (a separate, already hand-maintained concern — this importer only reads cells, never writes them) and any actor/audit trail (same deferred-pending-schema-decision reasoning as D-049).
**Consequences:** `@ipmat/question-engine` gains one new pure, tested module (also now publicly re-exporting `QuestionCandidateAiOutput` and the Phase 3.5 fixture file, both needed by `@ipmat/db`'s tests — the fixtures were previously only reachable via a relative cross-package path, the exact `rootDir` risk D-047 already flagged once). `@ipmat/db` gains one new narrow read/write port with Prisma and in-memory implementations. 28 new tests (6 pure-function, 13 in-memory repository, 7 Prisma-mock code-level, 2 running the REAL 7 Phase 3.5 fixtures through the unmodified pipeline and confirming the 2 `"validated"` ones import while the 5 `"review_required"` ones are refused) — 526 across the repo, typecheck/lint/build all clean. **No real `Question` row was created anywhere by this work** — no live database has ever been reachable in this environment, so every test here runs against `InMemoryQuestionImportRepository` or a mocked `PrismaClient`; `PrismaQuestionImportRepository` has never been exercised against real Postgres, the same standing caveat as every other `PrismaXRepository`. The published-question count remains 0. Still NOT done: actually invoking this importer against the real 7 Phase 3.5 candidates end to end (needs a reachable database), any human publish/reject decision against real content, and an import path for Hard/Extreme/Novel-tier (`"review_required"`) candidates (would need a genuinely new architecture decision, not a quick extension of this one).

**Addendum (same decision, follow-up correctness review): `assertCandidateIsImportable()` was missing a `candidate.blueprintId === blueprint.id` check, a real authority gap.** `validateBlueprintCompliance()` (inside the pipeline's own structural check) guarantees `candidate.questionDna` is consistent with the REAL blueprint tied to `candidate.blueprintId` — but only for that specific pair. Without independently re-checking the id match here, a caller could supply a genuinely-`"validated"` `candidate` alongside an unrelated `blueprint` object (different `examCode`/`sectionName`/`chapterName`); since `QuestionImportRepository` resolves `examId`/`sectionId`/`chapterId` from `blueprint`, validated content could be filed under an exam/section/chapter it was never actually checked against — the same "narrow the trust boundary at the point authoritative data is derived" lesson as D-048/D-049, one field the original pass missed. Fixed by adding the id check as the third guard in `assertCandidateIsImportable()` (new error code `blueprint_mismatch`), which both `PrismaQuestionImportRepository` and `InMemoryQuestionImportRepository` inherit for free since both call it first. 3 new tests (pure-function, in-memory, Prisma-mock) confirm the mismatch is refused and, for the Prisma path, that no query is ever issued. Also clarified in `prismaQuestionImportRepository.ts`'s own doc comment: the `(patternTaxonomyCellId, body)` idempotency guarantee is APPLICATION-LEVEL only (Postgres's documented "read-absence-then-insert" `Serializable` behavior) — there is no backing `@@unique` constraint, unlike the provenance rule's independent DB-level `CHECK`; adding one was considered and deliberately deferred as a schema migration, out of scope for this review. 529 tests across the repo, typecheck/lint/build all clean.
