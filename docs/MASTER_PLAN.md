### Phase 5B — Hypothesis + Confirmation + Mastery Engine + Targeted Repair (deterministic core) ✅ done (this pass)
Implements the HYPOTHESIS and CONFIRMED DIAGNOSIS layers Phase 5A left as type-only contracts, plus the actual Mastery Engine — still no UI, no persistence adapter, no real AI provider call, no adaptive question selection, no question-batch generation. See [PHASE_5B_REVIEW.md](PHASE_5B_REVIEW.md) for the full report.

- `autopsyHypothesisAiSchema` — the 5th `@ipmat/ai` task type; `generateHypothesis()` consumes `@ipmat/autopsy`'s `AutopsyOutput` (Phase 5A) through `generateStructured()`, refusing to call the provider at all when there's nothing to diagnose. Always returns `confirmationStatus: "awaiting_confirmation"` — never pre-confirmed.
- `applyConfirmationResponse()`/`confirmHypothesis()`/`rejectHypothesis()`/`correctHypothesis()`: the deterministic HYPOTHESIS -> CONFIRMED/REJECTED/CORRECTED state machine — a hypothesis reaches `"confirmed"` ONLY through an explicit student action; a correction is preserved as new evidence, never overwriting the original proposed explanation.
- `buildRepairPlan()`: turns a CONFIRMED (not "corrected") hypothesis into a target-identifying `RepairPlan` — concept, pattern family, taxonomy cell, error category, training mode, priority, real concept-graph prerequisites, confirmation traceability. - `mastery_states` gained one additive column, `component_detail: Json` (migration `0004_mastery_component_detail`, generated, not applied) — the 5 existing scalar columns are unchanged.
- 68 new tests across `@ipmat/autopsy` (hypothesis/confirmation/repair-plan/persistence, 30 tests) and `@ipmat/mastery` (component detail, mastery-state aggregation, persistence, one true cross-package integration test proving `@ipmat/attempt` -> `@ipmat/autopsy` -> hypothesis -> confirmation -> `RepairPlan` -> `MasteryState` end to end, 38 tests).

### Phase 5C — Persistence adapters + targeted repair selection + confirm/correct UI + adaptive selection
Depends on Phase 4B's persistence adapter pattern existing first (the same kind of Prisma-backed layer `@ipmat/attempt` needs, now also needed for `Autopsy`/`RepairPlan`/`MasteryState`). Split into three sub-phases so persistence, targeted repair, and global adaptive selection can each be reasoned about and tested in isolation, per the explicit architectural principle: **5C-2 is TARGETED REPAIR selection (one confirmed diagnosis -> one repaired question); 5C-3 is GLOBAL ADAPTIVE selection (what should this student practice next, in general). These are not the same concept and must not be merged.**

#### Phase 5C-1 — Persistence Boundary ✅ done (this pass)
- The first repository/adapter layer in this codebase (`packages/db/src/repositories`): `AutopsyRepository`/`RepairPlanRepository`/`MasteryStateRepository`, each a plain interface plus one concrete `PrismaXRepository` implementation, using Phase 5B's `toAutopsyPersistenceRecord()`/`toRepairPlanPersistenceRecord()`/`toMasteryStatePersistenceRecord()` mapping functions as their input and resolving the `ErrorTaxonomy.code`/`Concept.name` -> `id` foreign keys those functions deliberately left to the caller.
- Resolved docs/DECISIONS.md D-042's open tension: `mastery_states`'s 5 scalar columns widened to nullable `Float?` (migration `0005_mastery_state_nullable_measures`) — SQL `NULL` means "insufficient evidence," a real number (including `0`) means "measured," and a row is written once ANY attempt exists rather than only once every dimension has data. See D-043.
- Round-trip persistence semantics verified against `InMemoryXRepository` test doubles (no live database has ever been reachable), sharing validation logic (`packages/db/src/repositories/validation.ts`) with the Prisma-backed classes so the two cannot silently drift apart. An automated `domainBoundary.test.ts` proves no `packages/domain/*` package imports Prisma/`@ipmat/db`.
- 37 new tests (358 total), typecheck/lint/build clean across all 10 workspaces.

#### Phase 5C-2 — Diagnosis -> Repair (Targeted Repair Selection) ✅ done (this pass)
- New, database-free `packages/domain/repair-selection` (`@ipmat/repair-selection`): `selectRepairQuestion()` deterministically turns a CONFIRMED `RepairPlan` plus available Question DNA into either a selected question (with an explanation and the coverage gap it addresses) or an explicit `"no_match"` outcome — never an opaque AI call, never a silent substitution.
- Explicit, named, ORDERED match tiers (`direct_cell_and_trap` > `direct_cell` > `pattern_family_and_trap` > `trap_only` > `pattern_family` > `concept_fallback`, `matchTier.ts`) replace any black-box composite score; deterministic tie-breaking (`tieBreak.ts`) applies overuse avoidance, then a speed-weakness preference (reusing `@ipmat/autopsy`'s own `AUTOPSY_THRESHOLDS.SLOW_SPEED_RATIO`), then difficulty-tier proximity, then `questionId` as a final, always-decisive tie-break.
- Confirmation semantics re-verified at this package's own boundary (`RepairSelectionError("not_confirmed", ...)`) in addition to `buildRepairPlan()`'s existing gate — the same defense-in-depth discipline Phase 5C-1's repository layer established (D-043); a corrected hypothesis's free text is never auto-classified, because it never produces a `RepairPlan` to select from at all.
- 51 new tests (409 total) covering direct/concept/family/cell/repeated-error-category/speed/novelty/pressure repair, explicit fallback and no-match behavior, deterministic tie-breaking, overuse avoidance, malformed-DNA rejection, all four confirmation states, and one cross-package integration test (`Attempt` -> `AutopsyOutput` -> hypothesis -> confirmation -> `RepairPlan` -> repair selection -> selected Question DNA). See docs/DECISIONS.md D-044. Typecheck/lint/build clean across all 11 workspaces.

**Explicitly NOT done in 5C-1/5C-2** (by design): confirm/correct UI, any real AI provider call, any persistence adapter actually executed against a live database, and — critically — **adaptive question selection** (Phase 5C-3, not started): no code anywhere reads `MasteryState` to decide what a student should practice next in general.

- Wires 5C-1's persistence adapters and 5C-2's `selectRepairQuestion()` into an actual UI-facing flow.

**Exit criterion:** a wrong answer produces a hypothesis, the student can confirm or correct it in a real UI, and a confirmed diagnosis visibly changes what question the student sees next.

### Phase 7 — Vertical slice hardening
Dogfood internally, fix correctness issues found in generated content, tighten validation thresholds based on real rejection-rate data, write down what broke in [DECISIONS.md](DECISIONS.md). Only after this phase is genuinely solid does chapter two (or any breadth work) start.

## What should be implemented FIRST

Phase 1 → 2 → 3 → 3.1 → 3.1.1 → 4A → 5A → 5B → 5C-1 → 5C-2 are done. Next, in order: (1) actually run the real-Anthropic smoke test (`npm run smoke:anthropic --workspace @ipmat/question-engine`) — nothing about the pipeline's behavior against a real model is verified until this happens at least once, and this now covers 5 task types including the Phase 5B hypothesis call; (2) Phase 3.5 (run the pipeline against the remaining 7 Percentages taxonomy cells with a real API key) before Phase 4B's practice loop, since Phase 4B needs more than one published question to be a meaningful loop; (3) Phase 4B needs a Prisma-backed persistence adapter around `@ipmat/attempt`, not built yet since no live database has ever been reachable in this environment (the same pattern Phase 5C-1 already proved out for `Autopsy`/`RepairPlan`/`MasteryState`); (4) Phase 5C-3 (adaptive selection) and the confirm/correct UI need real attempt data from Phase 4B and an actually-reachable database, so they naturally sequence after it — the deterministic core through targeted repair selection (hypothesis generation, confirmation, RepairPlan, Mastery computation, persistence adapters, repair-question selection) is already done and tested against `FixtureProvider`/in-memory doubles.

## Explicit go/no-go gate before starting chapter two

Do not start a second chapter until: the Percentages taxonomy has real coverage above a self-chosen threshold, the validation pipeline's rejection rate is low enough that it isn't a full-time babysitting job, and at least one real student has completed the full loop (practice → wrong answer → autopsy → repair → improved subsequent attempt) at least once. If any of those isn't true, the fix is to fix the slice, not to add breadth.
