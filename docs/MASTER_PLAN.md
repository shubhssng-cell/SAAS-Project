An unconfirmed plan (awaiting/rejected/corrected) is excluded BEFORE ever calling `selectRepairQuestion()`, re-checking the same `confirmationSource.hypothesisConfirmedAt` invariant that package already enforces internally — defense-in-depth, not a restatement of its matching logic.
- A repair `no_match` never silently becomes "adaptive practice succeeded": the orchestrator's `diagnostics` object ALWAYS preserves the raw outcome from whichever engine(s) were consulted, regardless of the final `status`; a fallback to adaptive practice is marked `wasFallbackFromRepair: true`, controlled by a second named policy constant (`ALLOW_ADAPTIVE_FALLBACK_ON_REPAIR_NO_MATCH`).
- Prior exposure for repair-selection's own overuse avoidance is derived by REUSING `@ipmat/adaptive-selection`'s already-exported `computeExposureCounts()` (a Map -> array reshape, not a third counting pass).
- Action vocabulary is deliberately closed for V1 (`targeted_repair` | `adaptive_practice`) — Calculation Gym, Speed Lab, Trap Lab, Novelty Lab, Pressure Training, Mock Simulation, and Revision are named only as future values, never implemented, matching `RecommendedTrainingMode`'s own "grows deliberately" discipline (D-037). Each engine invocation is its own standalone, exported function (`attemptTargetedRepair()`, `attemptAdaptivePractice()`) sharing a common `{attempted, outcome}` shape a future provider would also implement.

### Phase 5E-1 — Training Systems Core Contract ✅ done (this pass) — shared contract only, no concrete providers
New, database-free `@ipmat/training-systems` domain package defines the common `TrainingSystemProvider` abstraction every future training mode (Calculation Gym, Speed Lab, Trap Lab, Novelty Training, Pressure Training, Overtraining exposure, Revision, Mock Simulation) will eventually conform to — none of those concrete modes is implemented here, and this unit does NOT touch `@ipmat/training-orchestration` or its action vocabulary at all (that wiring is explicitly a later 5E unit). See docs/DECISIONS.md D-053 for the full design, including the three adjustments made to the approved design before implementation (single-sourced `evaluate()`, strict `error` semantics, no shared ranking utility).

- A provider is NOT a second adaptive-selection engine — it answers only "is my one narrow training mode applicable right now, and if so, what does a qualifying question require," never "what's globally best for this student."
- `evaluate(context)` is the ONE authoritative applicability decision (`{applicable: false, reason, explanation} | {applicable: true, requirement, explanation}`). `select(context, applicability)` is called ONLY after an `applicable: true` evaluation, and its own return type (`TrainingSystemSelectionOutcome`) structurally EXCLUDES `not_applicable` — proven by a dedicated `@ts-expect-error` test, not just documented. `runTrainingSystemProvider()` is the canonical entry point joining both steps.
- `error` is reserved strictly for invalid/impossible execution conditions — never for "no candidate matched" (`no_eligible_question`) and never for "mode doesn't apply" (`not_applicable`). Every non-error outcome carries `diagnostics`; `error` deliberately does not (verified by test).
- The shared package ships NO ranking/filtering utility of any kind — only types, a diagnostics-default constructor, and the runner — so "a provider recreates adaptive-selection/repair-selection semantics" is structurally unavailable from the contract itself, not merely discouraged by convention. Provider-local selection remains legitimate only when genuinely intrinsic to one narrow mode, deterministic, bounded, and tested — or a provider may delegate entirely to `selectNextQuestion()`/`selectRepairQuestion()`'s public entry points over a requirement-filtered pool.
- 18 new tests (10 contract/runner behavioral, 6 compile-time regression guards, 2 auto-discovered by `domainBoundary.test.ts`) — 601 tests across the repo (up from 583), typecheck/lint/build clean across all 15 workspaces.

**Explicitly NOT done** (by design, this pass): any concrete provider, any change to `@ipmat/training-orchestration` or its `TrainingActionType`, any HTTP/API route, any UI, real AI calls, ML. `@ipmat/training-systems` has no implementation and no caller yet — it is a contract only.

### Phase 5E-2 — Calculation Gym ✅ done (this pass) — first concrete provider, no orchestration wiring
New, database-free `@ipmat/calculation-gym` domain package is the first concrete `TrainingSystemProvider` built against Phase 5E-1's contract — a narrow calculation/mechanical-friction training mode, explicitly NOT a second global adaptive engine, a generic arithmetic queue, a generic speed system, or a composite "calculation ability" score. See docs/DECISIONS.md D-054 for the full design, including the four adjustments made to the approved design before implementation (explicit friction-gap rule with named thresholds, `computationalLoad` treated strictly as a provisional proxy never presented as measured ability, independently-gated progression transitions, provider-local selection limited to exactly three approved tie-break steps).

- Conceptual weakness, calculation/mechanical weakness, and speed weakness are kept structurally distinct, never collapsed into one variable: `CalculationFrictionEvidence` compares accuracy conditioned on Question DNA's provisional `computationalLoad` metadata specifically, `frictionDetected` never fires on evidence that looks like ordinary conceptual weakness (equally low accuracy on both slices), and raw timing/speed data is never read by this provider at all.
- None of the ten candidate calculation dimensions named in the original design brief (fractions, ratios, decimals, estimation, simplification, shortcuts, etc.) are implemented — Question DNA has no existing tag for any of them, and inventing one was explicitly rejected as unrepresentable rather than narrowly scoped. Only `computationalLoad` (continuous) and `multi_step`/`time_pressured` `testingModes` (categorical) are used, both already-existing DNA fields.
- Three named, closed, PROVISIONAL progression stages (`foundational` -> `mixed` -> `time_pressured`), each transition gated on its OWN independent evidence slice — mastering an earlier stage is necessary but never sufficient to unlock a later one (a dedicated regression test proves a 100%-accuracy, foundational-only history advances to `mixed` but can never reach `time_pressured` on that evidence alone).
- Selection is provider-local (delegating to `selectNextQuestion()` would discard the computationalLoad-specific signal this provider exists to act on) and uses exactly three approved tie-break steps over the requirement-filtered pool: least prior exposure, computational-load proximity to the requirement's floor, lexicographic questionId — no composite score, no weighted ranking. `RepairPlan` is never read by this provider; `@ipmat/training-orchestration`'s existing repair-precedes-adaptive policy already means it's never consulted where a confirmed diagnosis applies.
- 40 new tests (5 friction-evidence, 7 progression, 6 applicability, 9 selection, 4 end-to-end provider integration, 5 compile-time regression guards, 2 dependency-boundary, 2 auto-discovered by `domainBoundary.test.ts`) — 641 tests across the repo (up from 601), typecheck/lint/build clean across all 16 workspaces.

**Explicitly NOT done** (by design, this pass): any change to `@ipmat/training-orchestration` or its `TrainingActionType` (no wiring into a real selection flow yet), any HTTP/API route, any UI, real AI/ML calls, any finer calculation-skill taxonomy, any real-data calibration of this provider's own provisional thresholds. Speed Lab, Trap Lab, Novelty/Pressure/Revision/Mock providers remain unbuilt.

### Phase 5E-3 — Speed Lab ✅ done (this pass) — second concrete provider, no orchestration wiring
New, database-free `@ipmat/speed-lab` domain package is the second concrete `TrainingSystemProvider` — a narrow, general time-efficiency training mode, explicitly NOT a second Calculation Gym, not a generic arithmetic queue, not the future Pressure Training system. See docs/DECISIONS.md D-055 for the full design, including the three adjustments made to the approved design before implementation (the third stage renamed and narrowed from "exam_pressure" to `time_constrained`, the expected-time tie-break's wording neutralized to an uncalibrated preference only, and the applicability denominator made explicit and immutable) and the genuine progression-gate design flaw found and fixed during implementation (see below).

- Calculation Gym and Speed Lab are kept structurally distinct: Speed Lab never reads `computationalLoad`, never compares a high-vs-low-load accuracy gap, and has no dependency on `@ipmat/calculation-gym`. Both may legitimately read the same raw `attemptRecords`/`candidates` for different questions — the same reuse-of-raw-evidence precedent already established between Calculation Gym and `@ipmat/adaptive-selection`.
- The applicability denominator (`eligibleGradedCount`) is exact and immutable: submitted, graded, validly timed, hint-free, non-`time_pressured`, `conceptualLoad` below a provisional threshold — regardless of correctness. Only `correctSlowCount` (correct AND `speedRatio >= AUTOPSY_THRESHOLDS.SLOW_SPEED_RATIO`, the existing canonical "slow" definition, reused directly) can trigger applicability; `incorrectSlowCount` is tracked from the same population and surfaced as diagnostic-only, explicitly never claiming to know whether wrongness reflects a conceptual or calculation difficulty.
- A genuine bug was found and fixed before landing: an initial rate-based progression gate is the mathematical complement of the applicability trigger over the same population, making later stages unreachable while still applicable. Both progression gates are now count-based (reusing `MASTERY_CONSTANTS.MIN_OBSERVATIONS_FOR_COMPONENT` a third time) over a slice DISJOINT from the applicability trigger's population, mirroring Calculation Gym's own foundational/mixed split — `steady_pace -> mixed_pace` reads low-`conceptualLoad` good-pace count, `mixed_pace -> time_constrained` reads the complementary (moderate/high) `conceptualLoad` slice independently.
- `time_constrained` requires the existing `testingModes.includes("time_pressured")` DNA fact, documented explicitly as representing only "this question carries a time constraint" — never claiming ownership of the future, broader Pressure Training system (sustained sequences, section constraints, switching).
- Selection is provider-local, exactly three approved tie-break steps over the requirement-filtered pool: least prior exposure, lowest `expectedTimeSeconds` (documented only as a deterministic preference for the tighter available time budget, never a claim of harder/better/maximum training value), lexicographic questionId — no composite score.
- 52 new tests (11 speed-evidence incl. every inclusion/exclusion condition individually, 9 progression, 7 applicability, 10 selection, 5 end-to-end provider integration, 6 compile-time regression guards, 2 dependency-boundary, 2 auto-discovered by `domainBoundary.test.ts`) — 693 tests across the repo (up from 641), typecheck/lint/build clean across all 17 workspaces.

**Explicitly NOT done** (by design, this pass): any change to `@ipmat/training-orchestration` or its `TrainingActionType`, any HTTP/API route, any UI, real AI/ML calls, any real-data calibration of this provider's own provisional thresholds, the future Pressure Training system itself. Trap Lab, Novelty/Pressure/Revision/Mock providers remain unbuilt.

### Phase 5E-4 — Trap Lab ✅ done (this pass) — third concrete provider, no orchestration wiring
New, database-free `@ipmat/trap-lab` domain package is the third concrete `TrainingSystemProvider` — "trap-associated failure recurrence," explicitly NOT another Autopsy, NOT a second RepairPlan engine, NOT a confirmed diagnosis of anything. See docs/DECISIONS.md D-056 for the full design, including three rounds of review adjustments before implementation (no mandatory concept scoping, distinct-questionId as the only hard recurrence gate with surface diversity kept diagnostic-only, and epistemic language tightened by wording rather than by adding a confidence field).

- Recurrence is evaluated at the error-taxonomy-**code** level (the finest-grained represented error unit in the current data model), aggregated **across the student's entire attempt history regardless of concept** — a code such as `base_confusion` recurring across two different concepts still triggers, proven by a dedicated cross-concept test. Different codes never combine merely because they share an `ErrorCategory`.
- `distinctFailingQuestionIds` (a deduplicated, SET-derived count) is the ONLY hard gate, reusing `AUTOPSY_THRESHOLDS.REPEATED_EVIDENCE_MIN_COUNT` directly — a single incorrect attempt, or the same question retried any number of times, can never trigger applicability. Taxonomy-cell/pattern-family diversity and hint-free/hint-assisted "resistance" (correct attempts against the same code) are computed and surfaced but never gate applicability, cancel recurrence, or become a score.
- Cumulative, explicitly no recency/decay: once a code reaches recurrence, later correct attempts never remove it — disclosed directly in the applicability `notes`, deferred to a future Revision/Overtraining/Exposure-control system rather than solved with an invented freshness/confidence number.
- No progression vocabulary: unlike Calculation Gym/Speed Lab, no continuous, graduated DNA dimension exists for "trap intensity" to gate stage transitions on, so none was invented.
- Optional `context.errorTaxonomy` enrichment never changes the applicability decision (only diagnostic label/category text, or a `taxonomy_enrichment_missing:<code>` note) — proven by a dedicated invariance test comparing omitted vs. empty vs. incomplete taxonomy lists against the identical attempt history.
- Every Trap-Lab-produced `explanation`/`notes`/diagnostic string is regression-tested to avoid "confirmed"/"proven"/"diagnos"/"student's reasoning" wording, asserting instead the accepted "trap-associated"/"trap-tagged" candidate-level phrasing.
- Lightest dependency set of any provider so far: `@ipmat/training-systems` + `@ipmat/autopsy` only (no `@ipmat/mastery` — its recurrence gate is a discrete count, not a statistical-reliability floor) and zero new provisional numeric constants introduced.
- 69 new tests (20 evidence, 12 applicability, 13 selection, 6 end-to-end/cross-domain-independence, 7 compile-time regression guards, 7 epistemic-language, 2 dependency-boundary, 2 auto-discovered by `domainBoundary.test.ts`) — 762 tests across the repo (up from 693), typecheck/lint/build clean across all 18 workspaces.

**Explicitly NOT done** (by design, this pass): any change to `@ipmat/training-orchestration` or its `TrainingActionType`, any HTTP/API route, any UI, real AI/ML calls, confirmed-diagnosis-based recurrence (would require a `TrainingSystemContext` extension), any recency/decay/exposure-control model. Novelty/Pressure/Revision/Mock providers remain unbuilt.

### Phase 5E-5 — Novelty Training ✅ done (this pass) — fourth concrete provider, no orchestration wiring
New, database-free `@ipmat/novelty-training` domain package is the fourth concrete `TrainingSystemProvider` — the first one whose trigger is EXPOSURE, not weakness. See docs/DECISIONS.md D-058 for the full design, including the design-review correction made before implementation: applicability must never depend on which candidates happen to be supplied, only on the student's own attempt history.

- Applicability is computed over Question DNA's existing, authoritative `noveltyLevel` field (`novel_representation`/`novel_combination`/`novel_context`) — never `testingModes`' coincidentally-named values, never the continuous/provisional `difficultyDimensions.representationNovelty` estimate.
- `evaluateNoveltyTraining()` reads only `context.studentId`/`context.attemptRecords` — `context.candidates` is read for the first time inside `selection.ts`. A candidate-pool-invariance test and a source-level (comment-stripped) regression test both prove this directly.
- A concept-specific standard-exposure baseline (`>= 3` standard-noveltyLevel attempts for THAT concept specifically) gates evaluation entirely — another concept's activity never satisfies it, proven by a dedicated cross-concept isolation test.

### Phase 5E-6 — Pressure Training ⛔ DEFERRED (this pass) — no package created; no persisted session/sequence/block identity exists to build a genuinely distinct provider on
A full design review was conducted and the review's own conclusion was to NOT implement. See docs/DECISIONS.md D-059 for the complete reasoning; summarized here:

- The repository was inspected directly (`@ipmat/attempt`, `@ipmat/mastery`, `@ipmat/training-systems`, and `packages/db/prisma/schema.prisma`) rather than assumed. No `sessionId`/`practiceBlockId`, no persisted attempt-sequence-membership construct, no cumulative block-level time budget, and no session-level switching state exist anywhere in the current schema.
- `AutopsyQuestionContext.sectionName` is static, per-question exam-section metadata (e.g. `"Quant"`) — not a dynamic session-transition marker, and must never be treated as one.
- `finalizedAt` (the only timestamp on an attempt) cannot safely define an intentional training sequence — timestamp adjacency does not distinguish a genuine sustained block from two unrelated attempts that merely happen to be next to each other in all-time chronological order.
- `testingModes.includes("time_pressured")` — the one pressure-adjacent signal that IS safely available — is already owned by `@ipmat/speed-lab`'s `time_constrained` stage (D-055).
- Implementing Pressure Training now would therefore do one of exactly two things, both rejected: duplicate Speed Lab, or invent unsupported session semantics from raw timestamps.
- **Minimum future prerequisite**: a general Practice Session / Block abstraction (session identity, attempt membership, start/end boundaries, a configured question-count target, a configured cumulative time budget, block-progress state, and eventually section/block configuration) — designed as GENERAL infrastructure, not Pressure-Training-specific plumbing, since it will also be the prerequisite for a future Mock/Simulation system. Designing that abstraction is itself a separate, future architectural unit, not decided here.

**No package was created. `packages/domain/pressure-training` does not exist.** `TrainingSystemContext`, `TrainingActionType`, `@ipmat/training-orchestration`, the `Attempt`/attempt-event schema, and the Prisma schema are all explicitly untouched.
