## What this project is

An AI-native mastery platform for Indian competitive exams. Currently building exactly one vertical slice: **IPMAT → Quant → Percentages**, end to end (Concept Universe → Examiner Lens → Question Universe → Question DNA → Generation → Validation → Student Attempt → Question Autopsy → Targeted Repair → Mastery). Read [docs/PRODUCT_SPEC.md](docs/PRODUCT_SPEC.md) before making product decisions and [docs/MASTER_PLAN.md](docs/MASTER_PLAN.md) before starting any new phase of work.

## Non-negotiable product rules

- **No confidence score.** Never add a field, endpoint, or UI element that claims to know how a student feels. Only observable performance (accuracy, speed, retries, hints, time-vs-expected) is measurable. See [docs/DECISIONS.md](docs/DECISIONS.md) D-005.
- **No fake AI, no fake analytics.** If something is presented as AI-driven or as real data, it must be backed by an actual model call or actual recorded attempts — never a stub dressed up as the real thing.
- **Autopsy is always a hypothesis until the student confirms it.** Never let unconfirmed diagnosis code paths write to mastery or trigger repair. See [docs/DECISIONS.md](docs/DECISIONS.md) D-006.
- **No hard-coded exam rules or pricing.** Exam/section/chapter structure and any pricing are data (DB rows), even when only one exam exists.
- **Content provenance is mandatory.** No question or content can be marked `published` without a `Provenance` record. Never use pirated/coaching-PDF/Telegram-dump content as a source, including for "just testing" purposes.
- **Question DNA is enforced, not conventional.** Don't add a code path that publishes a question with missing DNA fields, even temporarily.

## Working style for this repo

- **Vertical-slice discipline.** Before adding anything, check [docs/MASTER_PLAN.md](docs/MASTER_PLAN.md) §"What should explicitly NOT be built yet." If a request falls in that list, flag it back to the user rather than quietly building it — the plan is intentionally narrow right now.
- **Modular monolith boundaries are real, not aspirational.** Domain packages (`/packages/domain/*`) must not import Next.js, Prisma client, or a concrete AI provider directly — see [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) §6. If a change needs to violate this, that's a sign the boundary needs a design conversation, not a quick import.
- **All AI calls go through `@ipmat/ai`'s `generateStructured()`, with a Zod schema.** No raw prompt strings or unvalidated `JSON.parse` on a model response anywhere else in the codebase — this is real and built, not aspirational (Phase 3).
- **Expensive/slow AI work is meant to be a background job (BullMQ), never inline in a request handler — but that job/queue layer isn't built yet.** Phase 3's generation pipeline (`runGenerationPipeline()`) is a plain async function today, invoked directly. When a queue exists, it should wrap that function without changing its signature (it already takes an injected `AiProvider`) — don't design a job system that requires reshaping the pipeline.
- **No premature abstraction.** This codebase intentionally supports only IPMAT/Quant/Percentages right now — don't add multi-exam branching, plugin systems, or config layers for exams/chapters that don't exist yet just because the long-term vision has them. The schema is already shaped to generalize (see [docs/DATABASE.md](docs/DATABASE.md)); the code should stay simple until a second chapter is actually being built.
- **Tests on domain logic, not on AI call correctness.** Unit-test concept graph traversal, mastery computation, validation rules, and phase-curve logic with Vitest. AI call sites are tested against recorded fixtures (see [docs/AI_ARCHITECTURE.md](docs/AI_ARCHITECTURE.md) §6), not live provider calls.
- **Calendar-awareness (`computePrepPhase`, `applyCatchUp`, `PrepPhaseTemplate`, `CatchUpPlan`) is Phase 1 domain logic, not a deferred UI feature.** Only the phase *UI* is Phase 6 — don't push the schema or the pure functions back to "later" if asked to touch this area; see [docs/DECISIONS.md](docs/DECISIONS.md) D-009.
- **`AttemptEvent` is the source of truth for timing, not `Attempt`'s own columns.** A new timing question (e.g. "how long between hint and next click") is a new `event_type`, never a new column on `Attempt` or a new table. See [docs/DECISIONS.md](docs/DECISIONS.md) D-010.
- **`reasoning_text` (why the student answered this way) and `working_steps` (their scratch/computation) are different fields — don't collapse them.** See [docs/DECISIONS.md](docs/DECISIONS.md) D-011.
- **Error classification goes through the `ErrorTaxonomy` table by foreign key, never a free-form string.** See [docs/DECISIONS.md](docs/DECISIONS.md) D-012.
- **Concept relationships are one of 8 typed values, never a flattened "related."** `prerequisite`, `foundational`, `directly_related`, `commonly_combined`, `application`, `dependent`, `advanced_extension`, `related_but_distinct` each have a specific, non-overlapping meaning — see `packages/domain/concept-graph/src/types.ts` and [docs/DECISIONS.md](docs/DECISIONS.md) D-013 before adding a new edge or a new type. Every edge needs a real `rationale`, not just a label, and an honest `certainty` — don't mark something `confirmed` because it sounds plausible.
- **Examiner Lens never stores its own "combinations" list — always derive from the concept graph.** `deriveCombinations()` in `@ipmat/examiner-lens` is the only function that should populate that data; a stored, hand-maintained list is a bug waiting to drift from the graph. See [docs/DECISIONS.md](docs/DECISIONS.md) D-015.
- **A pattern family and a taxonomy cell are different things — don't conflate them.** `QuestionPatternFamily` describes a question's structure (can generate many questions); `PatternTaxonomyCell` is one concrete, coverage-tracked slice of that structure. See [docs/DECISIONS.md](docs/DECISIONS.md) D-014.
- **Coverage stage (`mapped`/`has_questions`/`validated`/`practice_ready`) is computed on every read, never a stored column.** Same rule as mastery. Use `computePatternFamilyReadiness()`/`buildQuestionUniverseSnapshot()` in `@ipmat/question-engine`, don't add a `coverageStage` column anywhere.
- **Never claim literal completeness in any user-facing or authored text.** "Every possible question," "mathematically complete," "fully covers," etc. are banned phrases — `findCompletenessClaims()` in `@ipmat/examiner-lens` is a concrete guard against this regressing; run authored content through it in tests. Only "known/mapped/covered/uncovered" language is allowed. See [docs/DECISIONS.md](docs/DECISIONS.md) D-007.
- **`@ipmat/ai` has zero dependency on domain packages — never import `@ipmat/concept-graph`/`examiner-lens`/`question-engine` into it.** Its Zod schemas deliberately restate the small controlled vocabularies rather than importing the domain types, both to avoid a package cycle (domain depends on `ai`, never the reverse) and because it's a genuine trust boundary. See [docs/DECISIONS.md](docs/DECISIONS.md) D-017.
- **Never trust an LLM's stated answer on its own.** Every numeric answer must be independently recomputed deterministically (`verifyComputation()` in `@ipmat/validation`, via `mathjs`) AND cross-checked against a second, independent AI call that never saw the first one's answer (`compareReverification()`). A mismatch on either is an automatic rejection, full stop — don't add a code path that lets a stated answer through on the AI's confidence alone.
- **Any AI-generated text that reaches `mathjs.evaluate()` (or any expression evaluator) must pass a strict arithmetic-only allowlist first — digits, whitespace, `.`, and `+ - * / ^ ( )` only, no comma.** It's untrusted input; see [docs/DECISIONS.md](docs/DECISIONS.md) D-018, D-028. Don't relax this to support fancier notation (or re-add a comma "for thousands separators" — mathjs treats it as a statement separator, not a grouping character, so it never did what it looked like it did) without re-checking the security tradeoff. `verifyComputation()` also enforces a 200-char length cap, a 15-digit numeric-literal cap, a 3-operator exponentiation-complexity cap, and a `1e12` result-magnitude cap, all checked before `evaluate()` is called — don't loosen these without a documented reason.
- **A pattern family and a blueprint and a candidate are three different things, in order of increasing concreteness.** `QuestionPatternFamily` = the structure; `QuestionBlueprint` = one concrete specification built deterministically from one `PatternTaxonomyCell` (no AI); a generated `QuestionCandidateAiOutput` = one AI attempt to fill that blueprint, not yet trusted. **Blueprint compliance checks EVERY field the candidate could drift on** — concept, pattern family, difficulty tier, every required testing mode, the specified trap, and the exact combination-concept set — not just `blueprintId`/concept/pattern family. See [docs/DECISIONS.md](docs/DECISIONS.md) D-022; if you add a new field to a blueprint, add its compliance check too.
- **Generated AI questions never auto-publish.** Hard/Extreme/Novel tiers always land in `review_required` regardless of how clean validation looks; only Standard/Advanced can reach `validated → published` without a human. See `computeLifecycleStatus()` in `@ipmat/question-engine` and [docs/DECISIONS.md](docs/DECISIONS.md) D-008.
- **Duplicate-risk detection is token-overlap similarity, not real semantic dedup, until there's an actual bank worth embedding.** Know this gap exists (D-019) rather than assuming it catches paraphrased duplicates.
- **Independent verifiers (reverification, judge) may ONLY receive `PresentedQuestionView`/`JudgeView` — never the full candidate object.** These types structurally exclude `correctAnswer`, `expectedAnswer`, `groundTruthDerivation`, `explanation`, `solutionSteps`, and `reasoning`. Never widen them, never pass the full candidate to a prompt builder for these two tasks, even "just to be safe" — that's exactly backwards. See `packages/domain/question-engine/src/verifierView.ts` and [docs/DECISIONS.md](docs/DECISIONS.md) D-020.
- **A generated `stem` must not state its own answer or leak internal metadata (e.g. `blueprintId`) verbatim.** `validateNoAnswerLeakageInStem()` in `@ipmat/validation` is a deliberately narrow, deterministic, non-semantic check — it catches a literal whole-token match, nothing more. Do not "improve" it into a keyword blacklist attempting to guess at paraphrased leakage; that was explicitly rejected as the wrong tool. See [docs/DECISIONS.md](docs/DECISIONS.md) D-029.
- **Concept names from AI output are matched by `normalizeConceptNameKey()` (trim/whitespace-collapse/lowercase), never raw string equality, and never fuzzy-matched.** "Ratio" and "ratio" must classify as the same concept; two genuinely different names (e.g. "Percentage" vs "Percentages") must never be silently folded together. See `packages/domain/concept-graph/src/graph.ts` and [docs/DECISIONS.md](docs/DECISIONS.md) D-030.
- **A numeric answer that can't be parsed fails closed (`unverifiable_answer`), never silently skips verification.** Don't reintroduce a code path where an unparseable `correctAnswer` is treated as "nothing to check" — see [docs/DECISIONS.md](docs/DECISIONS.md) D-024.
- **Difficulty dimensions on a blueprint are `difficultyCalibrationStatus: "provisional"` — never present them as calibrated fact.** No formula in this codebase has been validated against real question difficulty. Don't build a "smarter-looking" formula to make this feel more legitimate; that would hide the gap, not close it. See [docs/DECISIONS.md](docs/DECISIONS.md) D-021.
- **Before building any batch/loop generation, it MUST go through `validateGenerationLimits()` with an explicit `GenerationLimits` object, and the running-cost budget check pattern in `runGenerationPipeline()`.** No generation code path should be able to run without validated bounds on blueprint count, candidates per blueprint, retries, total attempts, and estimated budget. See [docs/DECISIONS.md](docs/DECISIONS.md) D-025.
- **A `null` estimated cost (an unrecognized/unpriced model) must NEVER be treated as `$0` by anything that spends real money.** `runGenerationPipeline()` checks `isKnownModel()` before making any AI call and refuses to run at all for an unpriced model — don't reintroduce a code path where an unknown cost is silently skipped over in a running-cost sum. See [docs/DECISIONS.md](docs/DECISIONS.md) D-027.
- **`AnthropicProvider.ANTHROPIC_MAX_OUTPUT_TOKENS_PER_CALL` is not just a formatting choice — it's the real bound on worst-case per-call cost, since the budget breaker is reactive (checked between calls, not during one).** If you ever raise it, re-read [docs/DECISIONS.md](docs/DECISIONS.md) D-031 and re-run `worstCaseSingleCallCostUsd()`'s tests first — that's the one place this coupling is made explicit and tested, don't let it drift back into an undocumented assumption.
- **Before claiming the AI pipeline "works," it must have been run against a real provider at least once — `FixtureProvider` passing is necessary, not sufficient.** As of Phase 3.1.1, it has NOT: check [docs/PHASE_3_1_1_REVIEW.md](docs/PHASE_3_1_1_REVIEW.md) for current status before assuming otherwise, and run `npm run smoke:anthropic --workspace @ipmat/question-engine` (never silently fall back to FixtureProvider if that key or call fails).
- **An `Attempt`'s `status` (`in_progress | submitted | skipped | abandoned`) is the one authoritative lifecycle state — `in_progress` is the only non-terminal value, and every terminal state (submitted/skipped/abandoned) is equally final.** Don't add a code path that transitions a finalized attempt back to `in_progress` or from one terminal state to another (e.g. "resubmit after skip") — if a future phase genuinely needs skip to be reversible, that's a deliberate new decision (see [docs/DECISIONS.md](docs/DECISIONS.md) D-035), not a quick patch to `skipAttempt()`.
- **`Attempt.chosenAnswer`, `isCorrect`, and `timeSpentSeconds` are always derived, never accepted as client input.** `chosenAnswer` comes from the last `answer_selected`/`answer_changed` event already recorded on the attempt; `isCorrect` comes from comparing it to the authoritative `Question.correctAnswer`; `timeSpentSeconds` is always `finalizedAt - startedAt`. `submitAttempt()` in `@ipmat/attempt` has no parameter through which any of these three could be passed in pre-computed — don't add one, even for a "trusted internal" caller. See [docs/DECISIONS.md](docs/DECISIONS.md) D-034.
- **`question_skipped` and `answer_submitted` events are only ever appended by `skipAttempt()`/`submitAttempt()` internally — never accept them as direct input to `recordAttemptEvent()`.** `RecordableAttemptEventInput` in `packages/domain/attempt/src/types.ts` excludes them at the type level for exactly this reason; don't widen that type to "make recording more flexible."
- **`AttemptEvent` payloads describe observable student actions only — never a confidence score, emotional state, or any inferred mental state.** This extends D-005 to the event log itself, and to the Autopsy/Mastery evidence contracts (`AttemptAutopsyEvidence`, `AttemptMasteryContribution` in `@ipmat/attempt`) — neither type has, or should ever gain, a field for confidence, motivation, intelligence, or emotion. See [docs/DECISIONS.md](docs/DECISIONS.md) D-034, D-035.
- **Answer-change history, Autopsy evidence, and Mastery-contribution data are all computed from an `AttemptState` on every call, never stored as their own columns** — the same "derive, don't cache" discipline as `MasteryState` and Examiner Lens combinations (D-015). Don't add a `changeCount`/`initialAnswer` column to `Attempt`; compute it with `deriveAnswerChangeHistory()`.
- **Autopsy is OBSERVATION -> EVIDENCE -> HYPOTHESIS -> CONFIRMED DIAGNOSIS — all four layers are now implemented (`@ipmat/autopsy`, Phase 5A + 5B).** `buildAutopsyOutput()` produces deterministic EVIDENCE; `generateHypothesis()` (the 5th `@ipmat/ai` task, `autopsy-hypothesis`) produces a real HYPOTHESIS, always `confirmationStatus: "awaiting_confirmation"`; `applyConfirmationResponse()` is the only path to CONFIRMED DIAGNOSIS. See [docs/DECISIONS.md](docs/DECISIONS.md) D-036, D-038.
- **A candidate error category is never a confirmed one, and a hypothesis cannot become confirmed except through an explicit student action.** `CandidateErrorEvidence` has no `confirmed` field, ever. `generateHypothesis()` cannot produce anything but `"awaiting_confirmation"` — there is no parameter through which a caller could construct a pre-confirmed hypothesis. `applyConfirmationResponse()`/`confirmHypothesis()`/`rejectHypothesis()`/`correctHypothesis()` (`@ipmat/autopsy`) are the ONLY functions that can move `confirmationStatus` forward, and each refuses (`already_decided`) once a response has already been applied. Don't add a code path that promotes a candidate or a hypothesis straight to confirmed — confirmation is exclusively the student's own response (D-006, D-038).
- **A "corrected" hypothesis is not accepted by `buildRepairPlan()` — only `confirmationStatus === "confirmed"` is.** The student's free-text correction (`studentCorrectionText`) has no structured category to target without another diagnosis pass; don't relax this check to "confirmed or corrected" without building that pass first (D-039).
- **Autopsy/behavior-signal thresholds (`FAST_SPEED_RATIO`, `SLOW_SPEED_RATIO`, `MULTIPLE_ANSWER_CHANGES`, `REPEATED_EVIDENCE_MIN_COUNT`) live in `@ipmat/autopsy`'s `AUTOPSY_THRESHOLDS`; mastery's `MIN_OBSERVATIONS_FOR_COMPONENT` lives in `@ipmat/mastery`'s `MASTERY_CONSTANTS` — one named, centralized place per package.** Don't hardcode a new magic-number threshold for a behavior/mastery signal elsewhere; add it there and mark it PROVISIONAL if it isn't calibrated against real data (it almost certainly isn't yet). A repeated-evidence count below `REPEATED_EVIDENCE_MIN_COUNT` (2) must never be reported as "repeated" — a single occurrence is not a pattern.
- **`@ipmat/autopsy` integrates the EXISTING `ErrorTaxonomy` — never build a second one.** Its `ErrorTaxonomyEntry` type restates the same shape `@ipmat/db/seed-data/errorTaxonomy.ts` already seeds (this package cannot depend on `@ipmat/db`, which pulls in Prisma — see docs/ARCHITECTURE.md §6), but the codes/categories/labels must stay the one shared vocabulary (D-013), not a parallel list.
- **No field, anywhere in `@ipmat/autopsy`, `@ipmat/attempt`, or `@ipmat/mastery`, may represent confidence, motivation, emotion, intelligence, anxiety, laziness, carelessness (as a trait), or intent — EXCEPT `AutopsyHypothesisAiOutput.modelConfidence`, which is explicitly the AI model's own confidence in one hypothesis, for ranking only, and must never be exposed or reinterpreted as the student's confidence in anything.** This extends D-005/D-006 to the Autopsy/Mastery layers. `careless_arithmetic` as an EXISTING `ErrorTaxonomy` *code name* (describing a calculation-error category, from Phase 1/2 seed data) is not an exception — this codebase never asserts "the student IS careless," only ever "this attempt's evidence pattern-matches that category," as an unconfirmed candidate. See D-038.
- **`RepairContext`/`RepairPlan` identify a target and a priority/training-mode — neither selects or generates follow-up questions.** Neither has a `followUpQuestionIds` field; picking actual questions remains Phase 5C work. `RecommendedTrainingMode`'s vocabulary is explicitly provisional (D-037) — grow it deliberately, the same way `ErrorTaxonomy` grows.
- **`@ipmat/mastery`'s `MasteryState` computation is multidimensional and NEVER collapses to one score.** `computeMasteryState()` returns 5 independently-nullable component measures (accuracy, speedRatio, noveltyHandling, pressurePerformance, patternCoverage) PLUS a full `MasteryComponentDetail` (counts, speed statistics, accuracy stability/stddev, difficulty/novelty/pressure breakdowns, error-recurrence streaks, coverage) — don't add a blended "overall mastery %" field anywhere. A headline measure is `null` (not `0`) below `MIN_OBSERVATIONS_FOR_COMPONENT` — that's "insufficient data," not "0% mastery." See D-040, D-041.
- **Mastery's "pattern coverage" (has THIS STUDENT attempted a cell) and question-engine's existing content coverage (does a pattern family have published questions at all) are different axes, both real — don't conflate them or build a second coverage model.** `@ipmat/mastery` reuses `@ipmat/question-engine`'s `computePatternFamilyReadiness()`/`PatternFamilyCoverage` directly for the content-readiness axis (D-040).
- **Pressure performance is read from Question DNA's `testingModes` including `"time_pressured"` — never inferred from how fast or slow a student happened to go.** Don't add a code path that infers "this was a pressure situation" from timing alone.
- **`toMasteryStatePersistenceRecord()` returns `null` (writes nothing) if any of the 5 headline measures is still `null`.** Don't change this to coerce a `0` default — the existing `mastery_states` columns are non-nullable `Float`, and writing `0` for "we don't know yet" would misrepresent absence of data as 0% mastery (D-042).
- **Training Systems and Adaptive Practice are different systems — never collapse them.** Adaptive Practice asks "what should this student practice next?"; a Training System asks "what performance dimension are we deliberately training?" A training session is selected by the chosen system's OWN `TrainingSystemProvider` (via `runTrainingSystem()` in `@ipmat/training-session`, routed through the existing orchestration registry), never by adaptive selection, and ignores repair plans. `@ipmat/training-session` has no selection/ranking logic and imports no engine, mastery, persistence or concrete provider (tested). See [docs/DECISIONS.md](docs/DECISIONS.md) D-075.
- **A Training Session is a thin row on the existing `PracticeBlock` — never a second attempt lifecycle, session table of its own, or stored progress.** Status, progress, enrollment and student are derived on every read; attempts are started through `PracticeApiService.startAttempt()` with the session's block id (an internal parameter no HTTP route may read — a client must never be able to name a block, an identity, or a clock). Training writes no autopsy, repair or mastery row. A session starts only when the system's own provider reports it applicable AND able to serve a published question (D-075).
- **Calculation Gym is the existing `@ipmat/calculation-gym` provider — never re-implement its policy in `@ipmat/training-session`, `@ipmat/practice-api` or the web.** A stage is DERIVED from persisted history on every read and is never stored (no stage column, no second state machine); a stage change is derived by re-running the system as of before the session's last finalized attempt. A stage must SERVE exactly what counts as that stage's progression evidence (`maxComputationalLoad`/`excludeMultiStep`/`excludeTimePressured`) — keep selection and progression shapes aligned. Don't weaken the provider's thresholds to make thin content activate it (use a labelled synthetic TEST DATA pool in a throwaway database), and never present a session summary as a score, a percentage, or proof of improvement (D-076).
- **Speed Lab is the existing `@ipmat/speed-lab` provider — reuse the session framework, never copy Calculation Gym's logic, and keep the two semantically independent.** Speed Lab never reads `computationalLoad`, never depends on `@ipmat/calculation-gym`, reuses `AUTOPSY_THRESHOLDS.SLOW_SPEED_RATIO` (no second slow/fast boundary), has no composite score/`priorityScore`/`targetSpeedRatio`, and treats incorrect-and-slow as diagnostic only. Its stage (`steady_pace` / `mixed_pace` / `time_constrained`) is derived from history and never stored, and a stage must SERVE exactly what counts as that stage's progression evidence (`minConceptualLoad`/`maxConceptualLoad`/`excludeTimePressured`/`requireTimePressured`). `time_constrained` is NOT Pressure Training. Don't put a ratio, threshold, count or "slow solver"-style claim in any student-facing text (D-077).
- **Trap Lab has NO stages and must never be forced into the staged UX.** Its catalog entry declares no `stages`; no session, question or completion view may show a stage, stage progress or a next-stage notice for it. Recurrence is per error-taxonomy CODE across all concepts (concept is not part of the trap's identity; `evaluate()` never populates `targetConceptName`), gated only by `AUTOPSY_THRESHOLDS.REPEATED_EVIDENCE_MIN_COUNT` DISTINCT failing question ids; correct attempts never cancel it and there is no decay. Never show a student the trap code, taxonomy-cell id, recurrence count, threshold, resistance or any diagnosis/trait wording ("diagnosed", "prone", "always", "bad at"), and never feed Trap Lab a confirmed Autopsy, RepairPlan or confidence. The provider's own not-applicable reason picks the authored hub sentence; the reason code is never shown (D-078).
- **Novelty Training is exposure-first, has NO stages, and its three styles are PEER categories — never a ladder, a weakness detector or a score.** It uses ONLY the categorical Question DNA `noveltyLevel` (never `testingModes` or `difficultyDimensions.representationNovelty`); `evaluate()` reads only the student's attempt history and must NEVER read `context.candidates` (applicability can't depend on available content; `no_eligible_question` is a select-time result, distinct from `not_applicable`); the baseline is concept-specific (distinct standard questions of THAT concept) and exposure counts are correctness-independent, cumulative, with no decay. Because its target (the globally least-exposed concept/style pair) ROTATES, the session objective must not name a concept (`conceptNotInObjective`). Never show a student a style name, `noveltyLevel`, taxonomy-cell id, exposure/baseline count or threshold, and never say they struggle with, are weak at, or lack adaptability for unfamiliar questions (D-079).

- **Pressure Training is evidenced by PRACTICE BLOCKS only, is a TIMED run, has NO stages, and is not Speed Lab or a weakness detector.** `@ipmat/pressure-training`'s `evaluate()` reads only `practiceBlocks`/`attemptRecords` (never candidates) and is `not_applicable` without block evidence however slow the single-question history; a training session IS one practice block, and finished runs become more of the evidence it reads. Its catalog entry allows only `fixed_duration` (`completionKinds`, enforced server-side; the duration is the block's time budget); the SERVER's clock ends the run and the web's "Time left" is display only. Never show a student the evidenced dimension, a threshold, gap, half-accuracy, block id or evidence count, never a pressure score or readiness, and never stress/fatigue/confidence/resilience wording or a claim that timed practice improves exam performance. The 5 s / 0.40 thresholds are PROVISIONAL (D-080).

- **Revision is concept-level re-exposure after a fixed, PROVISIONAL 14-day dormancy — never a decay model, a repair system, or a stage ladder.** A concept is eligible with >= 3 GRADED attempts (`submitted` with recorded correctness; skips never count; correctness is irrelevant) AND a most recent graded attempt >= `REVISION_CONSTANTS.DORMANCY_DAYS` old; the target is the longest-dormant eligible concept (concept name breaks ties); questions are published + structurally valid + exact concept, unseen taxonomy cell, then least exposure, then question id, and it NEVER switches concept to fill a pool. `evaluate()` reads only `studentId`/`attemptRecords`/`now` (never candidates, trap codes, novelty levels, blocks or mastery); time comes from `TrainingSystemContext.now` — a provider never reads a clock, and a missing `now` fails closed. Nothing about Revision is stored (no due flag/date/score/state column); it is derived from attempt history, and a revised concept stops qualifying because the revision attempt is ordinary evidence. It is registered in the orchestration registry but NEVER in `TRAINING_SYSTEM_PROVIDER_PRIORITY_ORDER` (student-chosen, not adaptive). Never show a student the day count, threshold, timestamp or graded-attempt count, and never claim they forgot anything or that revisiting improves retention (D-081).

- **The Exam Pack (`@ipmat/exam-pack`) describes an exam's KNOWLEDGE SPACE — never a student, and never anything the repository cannot source.** Generic modules never name a specific exam (IPMAT is data in `src/packs/`); the package imports only `@ipmat/concept-graph`; no field may represent mastery/confidence/attempts. A pack is validated and the service FAILS CLOSED on an invalid one. Ordering relations (`prerequisite`/`foundational`/`advanced_extension`) must be acyclic, checked per type and then on their union — NEVER across all types (the real graph links Ratio and Percentages in opposite directions via `prerequisite` and `dependent`); `application`/`dependent` may be cyclic; "unlocks" is the derived inverse of `prerequisite`, not a ninth type. Provenance is `kind` x `reviewState`: IPMAT is `authored` + `unvalidated` because no official syllabus exists in the repo — never label it `canonical`/`reviewed` without a real source and reviewer, never promote an inferred relation to `confirmed` unreviewed, and `imported` needs a `licenseRef`. Don't add IPMAT sections/terminology/skills the repository can't source. The database stores no provenance for exam structure, so persisted packs read back `unvalidated`. See D-082.
- **HISTORICAL EVIDENCE IS OBSERVED TESTING EVIDENCE, NOT A PREDICTION OF FUTURE EXAM CONTENT (`@ipmat/examiner-intelligence`).** Never add a field, query or text claiming likelihood, importance-for-the-next-exam, frequency-as-forecast or a predicted paper; a historical record supports only "observed in validated historical material". `ExamRelevance` (core/peripheral/stretch) is an EDITORIAL label carried with a rationale - never evidence. A `HistoricalQuestionRecord` is a CLASSIFICATION record: it must never gain a question body/options/answer/solution (copyrighted content is not stored; free-to-access is not free-to-copy), and the table has no such column. There is NO real historical IPMAT data in the repository - never invent "PYQs"; fixtures must be `dataOrigin: "fixture"` with a `fixtureLabel`, source type `original` and a `fixture:` reference, and are excluded from default queries. An AI-proposed classification is a `candidate_annotation` and never counts as intelligence until a named reviewer records `reviewed_validated`; default queries are reviewed + real-source only and always exam-scoped (a record of exam A must never surface for exam B). Reuse the existing Question DNA vocabulary (six difficulty dimensions, four novelty levels, `TestingMode` as "transformations", `ErrorTaxonomy` codes) - don't add dimensions/levels/traps, and don't cross-check difficulty against time/novelty/modes (long != hard, novel != difficult, time-pressured != hard). See D-083.
